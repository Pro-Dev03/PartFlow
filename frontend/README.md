# React + TypeScript + Vite

This template provides a minimal setup to get React working in Vite with HMR and some Oxlint rules.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Oxc](https://oxc.rs)
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/)

## React Compiler

The React Compiler is not enabled on this template because of its impact on dev & build performances. To add it, see [this documentation](https://react.dev/learn/react-compiler/installation).

## Expanding the Oxlint configuration

If you are developing a production application, we recommend enabling type-aware lint rules by installing `oxlint-tsgolint` and editing `.oxlintrc.json`:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "typescript", "oxc"],
  "options": {
    "typeAware": true
  },
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

See the [Oxlint rules documentation](https://oxc.rs/docs/guide/usage/linter/rules) for the full list of rules and categories.


# سياسة اشتراك PartFlow: بيانات محلية والتحقق السحابي إلزامي

## القرار المعتمد

تُحفظ عمليات المتجر محلياً في قاعدة بيانات SQLite، لكن لا يُسمح بتشغيل التطبيق أو تنفيذ عملية جديدة إلا عند وجود اتصال إنترنت والتحقق الناجح من الخادم السحابي.

الخادم هو المرجع الوحيد لصلاحية الحساب والاشتراك. أنت تدير ذلك يدوياً: عند انتهاء الاشتراك، تعطّل الحساب أو تحذفه من لوحة التحكم أو السكربت الإداري.

## توزيع المسؤوليات

```text
البيع والشراء والمخزون والعملاء والدفعات والتقارير
                         ↓
                   SQLite محلياً

الحساب وكلمة المرور وحالة الاشتراك ومدة الاشتراك والتعطيل
                         ↓
                 الخادم السحابي (Render)

نسخة احتياطية/مشاركة اختيارية للبيانات التشغيلية
                         ↕
            مزامنة ثنائية يدوية ومحمية
```

المصدر الذي تُنزّل منه المزامنة هو قاعدة Supabase عبر API الخادم. وتُدمج النسخة السحابية في SQLite المحلية عند الطلب. كما يستطيع المالك، عند الاتصال والتحقق الناجح، رفع العمليات المعلقة فقط من `sync_queue` إلى السحابة عبر مزامنة يدوية محمية. لا تُرفع قاعدة SQLite كاملة.

## آلية العمل

1. عند فتح التطبيق، يتحقق من وجود الإنترنت.
2. يرسل التطبيق طلب تحقق إلى الخادم باستخدام جلسة المستخدم.
3. يفحص الخادم أن الحساب موجود، نشط، وغير منتهٍ:
   - `is_active = true`
   - `subscription_status = active`
   - `subscription_expires_at` لم ينتهِ.
4. عند نجاح التحقق، يُفتح التطبيق وتُتاح العمليات المحلية في SQLite.
5. يستمر التطبيق في التحقق دورياً، وعند عودة الاتصال بعد انقطاعه.
6. قبل أي عملية حساسة مثل البيع أو الدفع أو تعديل المخزون، يجب أن يكون الاتصال والتحقق متاحين.
7. عند طلب سحب البيانات، يجلب الـBackend المحلي أحدث نسخة حساب المستخدم من Render المتصل بـSupabase، ثم يدمجها في SQLite المحلية بعد نجاح التحقق.
8. عند طلب رفع التغييرات، يرسل التطبيق العمليات المعلقة في `sync_queue` فقط، ويوقف العملية عند وجود تعارض مع نسخة سحابية أحدث.
9. إذا رفض الخادم الحساب بسبب التعطيل أو الحذف أو انتهاء الاشتراك، يمنع التطبيق العمليات الجديدة والمزامنة ويعرض صفحة انتهاء الاشتراك. لا تُحذف بيانات المتجر المحلية.

## سيناريو اشتراك 30 يوماً

- يبدأ الاشتراك يوم 1.
- في اليوم 30، إن لم يُجدّد العميل، تعطل حسابه أو تحذفه من الخادم.
- عند محاولة العميل فتح التطبيق أو تنفيذ عملية مع اتصال الإنترنت، يرفض الخادم التحقق فوراً.
- تبقى بياناته المحلية موجودة، لكن لا يمكنه إضافة بيع أو دفع أو تغيير مخزون.

## لماذا لا يوجد تشغيل أوفلاين للعمليات؟

لا يستطيع جهاز غير متصل بالإنترنت معرفة أنك عطلت الحساب على الخادم. لذلك، للسماح بإيقاف الحساب فوراً وبشكل موثوق، يكون الإنترنت شرطاً ضرورياً للتشغيل والعمليات.

التوقيع الرقمي مفيد فقط إذا أردنا السماح بالعمل دون إنترنت لمدة محددة؛ فهو يمنع تزوير الرخصة، لكنه لا يبلغ الجهاز المعزول بقرار تعطيل جديد. بما أن الأولوية هنا هي تحكمك الفوري بالحسابات، فلا تعتمد هذه السياسة على رخصة أوفلاين موقعة أو مهلة 24 ساعة.

## الفعالية ضد التلاعب

| السيناريو | النتيجة |
|---|---|
| تغيير حالة الاشتراك في قاعدة البيانات المحلية أو المتصفح | لا يكفي، لأن الخادم يتحقق من الحساب الحقيقي |
| تغيير تاريخ الجهاز | لا يمنح صلاحية؛ القرار من وقت وحالة الخادم |
| فصل الإنترنت بعد تعطيل الحساب | لا يمكنه بدء أو متابعة عملية جديدة، لأن الاتصال مطلوب |
| حذف الحساب أو تعطيله يدوياً من الخادم | يمنع الاستخدام عند التحقق التالي، وبشكل فوري للعمليات التي تتطلب التحقق |
| تعديل ملفات التطبيق من خبير | يقلل التحقق الإلزامي الأثر، لكنه لا يضمن منع نسخة معدلة 100% على جهاز يملكه المستخدم |

## ضوابط التنفيذ المطلوبة

- لا تعتمد أبداً على `subscription_status` محفوظ محلياً كقرار للسماح.
- اجعل Endpoint التحقق محمياً بالجلسة ويعيد رفضاً واضحاً للحساب غير النشط أو المنتهي.
- اجعل الواجهة تقفل العمليات عند فشل التحقق، مع رسالة عربية مفهومة.
- استمر في حفظ كل بيانات المتجر في SQLite محلياً، ولا تحذفها عند انتهاء الاشتراك.
- اجعل المزامنة الثنائية يدوية ومحصورة بالمالك: سحب من Supabase/Render إلى SQLite ورفع العمليات المعلقة من SQLite إلى السحابة فقط، مع كشف التعارضات وعدم حذف البيانات المحلية قبل نجاح العملية.
- وقّع نسخة تطبيق Electron وتحديثاته في الإنتاج لتقليل العبث بملفات البرنامج.
- احمِ حساب Render وقاعدة البيانات ومفاتيح البيئة؛ لا تضع كلمات مرور أو مفاتيح خاصة في التطبيق أو المستودع.

## الحكم النهائي

هذه أبسط سياسة متوافقة مع أولويتك:

- البيانات والعمليات التشغيلية محلية.
- الإنترنت والتحقق السحابي إلزاميان للتشغيل ولتنفيذ العمليات.
- المزامنة السحابية متاحة يدويًا في الاتجاهين عبر قائمة عمليات محمية، ولا تغيّر قاعدة العمل المحلية إلى قاعدة سحابية.
- تعطيلك اليدوي للحساب من الخادم يمنع العميل فور تحقق التطبيق.
- لا توجد مهلة أوفلاين ولا رخصة رقمية قصيرة؛ المزامنة منفصلة عن قرار السماح بالعمل.

الثمن الواضح: لا يمكن للمتجر تنفيذ عمليات عند انقطاع الإنترنت. هذا هو المقابل الضروري للتحكم الفوري والقوي في الحسابات من الخادم.

## ملاحظة مهمة عن اكتمال المزامنة

واجهة «مزامنة سحابية الآن» تستدعي مساراً محلياً يجلب نسخة الحساب من Render/Supabase إلى SQLite. وتوجد واجهة «رفع التغييرات المحلية» لمعالجة `sync_queue` يدويًا من SQLite إلى PostgreSQL بعد التحقق، مع كشف التعارضات وتقرير النجاح والفشل.

## حالة التطبيق الحالية

تم تطبيق السياسة في الكود كما يلي:

- صفحة الدخول لا تعرض اختياراً بين اتصال سحابي ومحلي؛ تسجيل الدخول يذهب إلى Render دائماً.
- `ApiClient` يوجّه عمليات المتجر إلى خدمة SQLite المحلية فقط.
- قبل كل طلب تعديل (`POST` و`PUT` و`PATCH` و`DELETE`) يتحقق التطبيق من Render؛ عند انقطاع الإنترنت أو رفض الحساب لا تُرسل العملية الجديدة. زر الرفع يعالج فقط العمليات المعلقة الموجودة مسبقاً في `sync_queue`.
- خدمة الـBackend المحلية في Electron مهيأة لتفويض التحقق إلى Render أيضاً، حتى لا يكفي استدعاء localhost مباشرة لتجاوز الاشتراك.
- تبويب قاعدة البيانات يعرض زر «مزامنة سحابية الآن» لتنزيل نسخة الحساب إلى SQLite، وزر «رفع التغييرات المحلية» لرفع العمليات المعلقة يدويًا.
- حذف بيانات التشغيل السحابية والمحلية متاح للمالك الإداري فقط مع تأكيد صريح، ولا يحذف حساب المالك أو الإعدادات أو بنية قاعدة البيانات.
- قائمة Electron وشريطها لا يقدمان تبديل Online/Offline؛ الاتصال يُدار تلقائياً وفق تحقق السحابة.
- عند انقطاع الإنترنت أثناء الاستخدام، تُغلق الجلسة ويعاد المستخدم إلى صفحة الدخول.
- أزيلت الرخصة الرقمية، وربط الأجهزة، ومهلة التشغيل الأوفلاين، ومسودات البيع الأوفلاين من المسار التشغيلي.

بالتالي، كلمة «محلي» في هذه الخطة تعني مكان تخزين بيانات المتجر فقط، ولا تعني السماح بالعمل دون اتصال.
