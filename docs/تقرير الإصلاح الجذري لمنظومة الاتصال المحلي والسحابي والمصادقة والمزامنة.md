# تقرير الإصلاح الجذري لمنظومة الاتصال المحلي والسحابي والمصادقة والمزامنة

## PartFlow

### الهدف الرئيسي

نريد إعادة تنظيم منظومة:

* الاتصال المحلي.
* الاتصال السحابي.
* تسجيل الدخول قبل الدخول للنظام.
* Access Token / Refresh Token.
* حماية التوكن.
* التحقق من الاشتراك.
* انقطاع الإنترنت.
* انتهاء الاشتراك.
* مزامنة البيانات بين Local وCloud.
* أزرار رفع وتنزيل البيانات.

بحيث تكون المنظومة واضحة، مستقرة، وآمنة، ولا يحدث تسجيل خروج تلقائي بسبب أخطاء مؤقتة أو مشاكل تقنية يمكن استرجاعها.

**قاعدة العمل الأساسية المطلوبة:**

> يجب أن يكون تسجيل الخروج التلقائي بسبب أحد سببين فقط:
>
> 1. انقطاع الإنترنت بشكل فعلي يمنع النظام من الاستمرار في الاتصال المطلوب.
> 2. انتهاء الاشتراك فعليًا ومؤكدًا من مصدر الاشتراك السحابي.
>
> جميع أخطاء المصادقة المؤقتة، انتهاء Access Token مع وجود Refresh Token، أخطاء Render، أخطاء 401 القابلة للاسترجاع، مشاكل Refresh Token المؤقتة، أو فشل API مؤقت، لا يجب أن تؤدي مباشرة إلى Logout.

---

# 1. فصل Local وCloud قبل تسجيل الدخول

هذه نقطة أساسية ويجب مراجعتها من الجذر.

عند فتح PartFlow وقبل تسجيل الدخول يجب أن يكون لدى النظام وضع اتصال واضح:

### Local Mode

عند اختيار:

**محلي**

يجب أن يكون المسار:

```text
Frontend
   ↓
Local Backend
   ↓
SQLite
```

ولا يجب أن يقوم النظام أثناء تشغيل Local Mode باستخدام Cloud Database كقاعدة بيانات تشغيلية.

لكن يوجد استثناء واحد:

### التحقق من الاشتراك

الوضع المحلي يحتاج إلى التحقق من صلاحية الاشتراك من الخدمة السحابية.

أي:

```text
Local Mode

Business Data
    ↓
Local Backend
    ↓
SQLite

Subscription Verification
    ↓
Cloud API
    ↓
Cloud Subscription Service / Supabase
```

أي أن Cloud هنا يستخدم فقط للتحقق من الاشتراك والمصادقة المطلوبة، وليس كمصدر للبيانات التشغيلية المحلية.

---

# 2. Cloud Mode

عند اختيار:

**سحابي**

يجب أن يكون المسار:

```text
Frontend
   ↓
Cloud API / Render
   ↓
Supabase
```

ولا يجب أن يستخدم Cloud Mode قاعدة SQLite المحلية للبيانات التشغيلية.

بمعنى:

```text
Cloud Mode
❌ لا SQLite للبيانات التشغيلية
❌ لا Local Business Data
✅ Render API
✅ Supabase
```

يجب مراجعة جميع الخدمات والـ hooks والـ API clients للتأكد من عدم وجود أي طلبات محلية يتم تنفيذها أثناء Cloud Mode.

---

# 3. اختيار الاتصال يجب أن يكون قبل Authentication

يجب أن يكون Connection Mode جزءًا أساسيًا من دورة Authentication.

الترتيب الصحيح:

```text
فتح التطبيق
      ↓
اختيار Local / Cloud
      ↓
تثبيت Connection Mode
      ↓
عرض Login
      ↓
تنفيذ Login حسب الوضع المختار
      ↓
إنشاء الجلسة
      ↓
التحقق من الاشتراك
      ↓
الدخول إلى النظام
```

ولا يجب أن يحدث:

```text
Login
 ↓
إنشاء Cloud Session
 ↓
ثم اكتشاف أن المستخدم اختار Local
```

أو العكس.

يجب أن يعرف النظام منذ البداية أي Backend يجب استخدامه.

---

# 4. ممنوع خلط Sessions بين Local وCloud

المحادثة السابقة كشفت مشكلة مهمة:

كان من الممكن أن يكون التطبيق في:

```text
mode = local
```

ولكن توجد Session سحابية قديمة، وبعد فشل التحقق منها كان التطبيق يقوم بإخراج المستخدم.

هذه البنية يجب إنهاؤها جذريًا.

يجب أن تكون لكل وضع جلسة واضحة:

```text
LOCAL SESSION
    ↓
Local Access Session

CLOUD SESSION
    ↓
Cloud Access Session
```

وتغيير الوضع يجب أن يؤدي إلى إنشاء/استخدام الجلسة الصحيحة فقط.

وجود Cloud Token قديم لا يعني أن Local Session أصبحت غير صالحة.

وجود Local Session لا يعني أن Cloud Session يجب أن تُستخدم لتشغيل البيانات.

# 5. حماية Tokens – إزالة التخزين الحساس من localStorage

يجب مراجعة منظومة التوكن بالكامل.

حاليًا المحادثة أظهرت استخدام مفاتيح مثل:

```text
auth_token
refresh_token
cloud_token
cloud_refresh_token
```

داخل `localStorage`.

هذا يجب تغييره بالنسبة للتوكنات الحساسة.

## المطلوب

استخدام:

```text
HttpOnly
Secure
SameSite
```

Cookies بالنسبة إلى:

* Refresh Token.
* Session Token إذا كان التصميم يسمح بذلك.
* أي credential طويل العمر.

خصوصًا:

```text
Refresh Token
```

يجب ألا يكون قابلًا للقراءة بواسطة JavaScript.

### المطلوب:

```http
Set-Cookie:
  refresh_token=...
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/api/v1/auth
```

ويجب ضبط `Domain` و`Path` حسب البنية الفعلية للتطبيق.

# 6. Access Token

إذا كان التصميم الحالي يحتاج Access Token قصير العمر، يمكن إبقاؤه في الذاكرة فقط بدل تخزينه دائمًا في localStorage.

المطلوب:

```text
Access Token
    ↓
Memory
    ↓
API requests
```

وعند انتهاء صلاحيته:

```text
Access Token expired
       ↓
Refresh
       ↓
New Access Token
       ↓
Continue session
```

بدون Logout.

أما Refresh Token:

```text
Browser
   ↓
HttpOnly Secure Cookie
   ↓
Backend
```

ولا يستطيع JavaScript قراءته.

---

# 7. حماية Refresh Token

يجب إعادة تصميم Refresh Token flow بالكامل.

المحادثة السابقة كشفت وجود مشكلة محتملة في:

**Token Refresh Race**

خصوصًا عند وجود أكثر من نافذة Browser.

يجب أن يكون هناك نظام Refresh آمن يمنع:

```text
Window A → refresh
Window B → refresh
Window A token becomes invalid
Window B token becomes invalid
```

المطلوب:

### Single-flight Refresh

إذا كان هناك Refresh جارٍ بالفعل:

```text
Request A
   ↓
Refresh started

Request B
   ↓
Wait for existing refresh
```

ولا يقوم كل Request بعمل Refresh مستقل.

---

# 8. Refresh Token Rotation

إذا كان Backend يدعم Refresh Token Rotation، يجب تطبيقها بشكل صحيح:

```text
Old Refresh Token
       ↓
Refresh
       ↓
New Refresh Token
       ↓
Old token invalidated
```

لكن يجب الانتباه إلى تعدد النوافذ والأجهزة حتى لا يؤدي Rotation إلى Logout خاطئ.

يجب وجود آلية آمنة للتعامل مع:

* Refresh متزامن.
* إعادة المحاولة.
* انتهاء Access Token.
* فشل الشبكة أثناء Refresh.
* استجابة Server مؤقتة.
* Refresh Token فعليًا غير صالح.

---

# 9. القاعدة الجديدة لتسجيل الخروج التلقائي

هذه أهم نقطة في التقرير.

يجب إزالة أي منطق من نوع:

```text
401 → logout
```

أو:

```text
refresh failed → logout
```

أو:

```text
cloud validation failed → logout
```

أو:

```text
Render error → logout
```

أو:

```text
network request failed → logout
```

بشكل مباشر.

# 10. تصنيف أخطاء Authentication

يجب أن يتم تصنيف الأخطاء.

## الحالة A – Access Token منتهي

مثال:

```text
401
```

والـ Refresh Token صالح.

النتيجة:

```text
Refresh
↓
New Access Token
↓
Retry request
↓
Continue
```

**لا Logout.**

---

## الحالة B – Refresh مؤقت فشل بسبب الشبكة

مثال:

```text
Network Error
Timeout
DNS
Render unavailable
Connection reset
```

النتيجة:

```text
Keep session
↓
Mark authentication verification as pending
↓
Retry with backoff
```

ولا يتم Logout مباشرة.

---

## الحالة C – Server Error

مثال:

```text
500
502
503
504
```

النتيجة:

```text
Keep session
↓
Retry later
```

ولا Logout.

---

## الحالة D – 401 قابل للاسترجاع

إذا كان Access Token غير صالح لكن Refresh Token موجود:

```text
401
 ↓
Refresh
 ↓
Retry
```

ولا Logout.

---

## الحالة E – انتهاء الاشتراك الحقيقي

يجب أن يكون هناك رد صريح من Cloud Subscription Service، مثل:

```text
403
SUBSCRIPTION_EXPIRED
```

أو Error Code موحد خاص بانتهاء الاشتراك.

عندها فقط:

```text
Logout / Subscription Expired Screen
```

لأن الاشتراك انتهى فعليًا.

---

# 11. مصدر الحقيقة للاشتراك

مدة الاشتراك لا يجب أن تعتمد على ساعة جهاز المستخدم.

يجب أن يكون المصدر النهائي:

```text
Cloud Subscription Service
```

أو المصدر المركزي للاشتراكات.

لا نريد:

```text
Local PC Time
```

كمصدر نهائي لقرار انتهاء الاشتراك.

يجب منع المستخدم من تغيير ساعة الجهاز والتأثير على حالة الاشتراك.

القرار يجب أن يأتي من Server.

---

# 12. Local Mode + Subscription

في Local Mode:

```text
Business Data
    ↓
SQLite
```

لكن:

```text
Subscription
    ↓
Cloud
```

عند نجاح التحقق:

```text
subscription = active
```

يستمر المستخدم.

إذا فشل الاتصال مؤقتًا:

```text
subscription status = verification_pending
```

ولا يتم Logout فورًا.

إذا أصبح الاشتراك منتهيًا فعليًا وتم تأكيد ذلك من Cloud:

```text
SUBSCRIPTION_EXPIRED
```

عندها فقط يتم إيقاف الجلسة/الدخول.

---

# 13. انقطاع الإنترنت

يجب التعامل معه كحالة مستقلة.

عند انقطاع الإنترنت:

```text
navigator offline
```

أو فشل اتصال الشبكة فعليًا.

لا يجب مسح:

* Local Session
* Access State
* Local Data
* SQLite
* User configuration

فقط يتم الدخول في:

```text
OFFLINE / CONNECTION LOST
```

وعند عودة الإنترنت:

```text
ONLINE
 ↓
Reconnect
 ↓
Refresh / Validate
 ↓
Continue
```

---

# 14. ملاحظة مهمة حول Logout عند انقطاع الإنترنت

المطلوب النهائي من النظام حسب هذا التقرير:

> لا يتم Logout لمجرد أن طلبًا واحدًا فشل.

يجب أولًا التحقق من أن المشكلة:

```text
Actual Network Loss
```

وليست:

```text
API 500
API 502
API 503
Timeout
Temporary Render issue
Temporary Refresh failure
Temporary Cloud validation failure
```

ويجب عدم اعتبار كل هذه الحالات "انقطاع إنترنت".

# 15. المزامنة Local → Cloud

يوجد حاليًا زر:

**رفع التغييرات للسحابة**

ويجب تثبيت وظيفته بشكل واضح.

المسار الصحيح:

```text
SQLite
   ↓
Local Sync Engine
   ↓
Local Backend
   ↓
Cloud API
   ↓
Supabase
```

أي أن الزر لا يجب أن يرسل بيانات SQLite مباشرة من Frontend إلى Supabase.

---

# 16. زر رفع البيانات المحلية إلى السحابة

يجب أن يقوم الزر فعليًا بـ:

```text
قراءة العمليات المحلية غير المتزامنة
        ↓
تحويلها إلى Sync Operations
        ↓
إرسالها إلى Local Backend
        ↓
Local Backend authenticates
        ↓
Cloud validation
        ↓
Cloud API
        ↓
Apply operations
        ↓
Return result
        ↓
Mark successful operations as synced
```

ويجب عرض نتيجة حقيقية للمستخدم:

```text
تم رفع:
15 عملية

فشل:
0

متبقي:
0
```

وليس مجرد:

```text
200 OK
```

---

# 17. زر تحميل البيانات من السحابة

زر:

**تنزيل من السحابة**

يجب أن يكون مساره واضحًا:

```text
Cloud API
   ↓
Supabase
   ↓
Cloud Data
   ↓
Sync Engine
   ↓
Local Backend
   ↓
SQLite
```

ويجب ألا يقوم Frontend بتجاوز Backend والاتصال مباشرة بقاعدة البيانات.

---

# 18. حماية المزامنة من تكرار البيانات

يجب أن تكون كل عملية Sync قابلة للتعريف بشكل فريد:

```text
operation_id
```

أو آلية Idempotency مناسبة.

إذا أرسلنا العملية مرتين:

```text
operation #123
```

يجب ألا يتم إنشاء:

```text
Sale #1
Sale #2
```

بسبب إعادة الإرسال.

بل:

```text
operation #123
already applied
```

ويتم تجاهل التكرار بأمان.

---

# 19. التعامل مع فشل المزامنة

إذا فشلت عملية واحدة:

```text
Operation A → success
Operation B → failed
Operation C → success
```

يجب ألا يتم اعتبار المزامنة كلها فاشلة.

يجب تسجيل:

```text
processed
failed
skipped
pending
```

مع سبب الخطأ.

# 20. عدم الخلط بين Connection Mode وSync

هذه نقطة مهمة جدًا.

وجود:

**مزامنة البيانات المحلية سحابيًا**

لا يعني أن Local Mode أصبح Cloud Mode.

مثال:

```text
Local Mode
    ↓
SQLite هي قاعدة البيانات التشغيلية
    ↓
User presses Sync
    ↓
Cloud receives synchronization
```

بعد انتهاء Sync:

```text
Still Local Mode
```

وليس:

```text
Cloud Mode
```

والعكس صحيح.

# 23. Event System

إذا كان النظام يستخدم:

```text
partflow:auth-invalidated
```

يجب عدم استخدام Event عام يحمل معنى مبهمًا مثل:

```text
expired
```

لأن كلمة `expired` قد تعني:

* Access Token expired
* Refresh Token expired
* Session expired
* Subscription expired

وهذه حالات مختلفة تمامًا.

يجب استخدام Events محددة:

```text
AUTH_ACCESS_TOKEN_EXPIRED
AUTH_REFRESH_REQUIRED
AUTH_NETWORK_UNAVAILABLE
AUTH_VERIFICATION_PENDING
SUBSCRIPTION_EXPIRED
```

وبالتالي:

```text
SUBSCRIPTION_EXPIRED
```

فقط هو الذي يستطيع الوصول إلى مسار Logout بسبب الاشتراك.

---

# 24. عدم الاعتماد على نص Error Message

يجب ألا يكون القرار مبنيًا على:

```text
message.includes("expired")
```

أو:

```text
reason.includes("expired")
```

لأن هذا يؤدي إلى أخطاء خطيرة.

القرار يجب أن يعتمد على:

```text
error.code
```

مثال:

```text
SUBSCRIPTION_EXPIRED
```

وليس:

```text
message = "Cloud session expired"
```

* HttpOnly Cookies.
* Secure Cookies.

* Session expiration.

# 30. المطلوب من Backend

```text

SERVICE_UNAVAILABLE
SUBSCRIPTION_EXPIRED
SUBSCRIPTION_VERIFICATION_PENDING
```

ويجب ألا تستخدم الواجهة Status Code وحده لاتخاذ قرار Logout.

مثلاً:

```text
401
```

لا يعني دائمًا:

```text
Logout
```

بل يعني أن الواجهة يجب أن تعرف هل يمكن عمل Refresh أم لا.

---

# 32. Logout النهائي

يجب أن يكون هناك Function مركزية واحدة فقط مثل:

```text
performFinalLogout(reason)
```

ولا يجوز أن تقوم كل صفحة أو كل API hook بعمل Logout بنفسها.

الأسباب المسموحة يجب أن تكون محددة.

مثال:

```text
SUBSCRIPTION_EXPIRED
NETWORK_LOSS_FINAL
USER_REQUESTED_LOGOUT
```

ويجب منع أي Component آخر من اختراع سبب Logout خاص به.

# 34. معايير القبول النهائية

لن يعتبر العمل منتهيًا إلا إذا تحققت جميع النقاط التالية:

### Connection

* [ ] Local Mode يستخدم Local Backend + SQLite للبيانات التشغيلية.
* [ ] Cloud Mode يستخدم Cloud API + Supabase.
* [ ] لا يوجد خلط بين Local وCloud.
* [ ] اختيار الاتصال يتم قبل Login.
* [ ] تغيير Connection Mode لا يسبب استخدام Session قديمة من الوضع الآخر.

### Authentication

* [ ] Access Token يمكن تجديده بدون Logout.
* [ ] Refresh Token محمي بـ HttpOnly Cookie.
* [ ] Refresh Token غير موجود في localStorage.
* [ ] Refresh يعمل بأمان مع أكثر من Tab.
* [ ] لا يوجد Refresh Race.
* [ ] لا يتم تسجيل Tokens في Logs.

### Subscription

* [ ] الاشتراك يتم التحقق منه من Cloud.
* [ ] لا يعتمد القرار على ساعة الجهاز.
* [ ] `SUBSCRIPTION_EXPIRED` فقط يؤدي إلى انتهاء الجلسة بسبب الاشتراك.
* [ ] أخطاء Cloud المؤقتة لا تؤدي إلى Logout.

### Network

* [ ] Network failure لا يمسح Session.
* [ ] Render temporary failure لا يمسح Session.
* [ ] 500/502/503/504 لا تؤدي إلى Logout.
* [ ] عودة الإنترنت تعيد التحقق تلقائيًا.

### Sync

* [ ] زر رفع البيانات يعمل فعليًا Local → Cloud.
* [ ] زر تنزيل البيانات يعمل فعليًا Cloud → Local.
* [ ] لا يوجد تجاوز للـ Backend.
* [ ] العمليات لا تتكرر.
* [ ] العمليات الفاشلة يتم تسجيلها وإظهارها.
* [ ] النتائج الحقيقية تظهر للمستخدم.
* [ ] Sync لا يغير Connection Mode.

# 35. اختبارات إلزامية قبل التسليم

يجب على المطور تنفيذ اختبار E2E فعلي وليس مجرد مراجعة الكود.

السيناريو الأساسي:

```text
1. Open PartFlow
2. Select Local
3. Login
4. Verify SQLite
5. Verify Cloud subscription
6. Disconnect Internet
7. Continue working locally
8. Confirm no unexpected logout
9. Restore Internet
10. Verify reconnection
11. Expire Access Token artificially
12. Verify automatic refresh
13. Force temporary 500 from Cloud
14. Confirm user remains logged in
15. Simulate SUBSCRIPTION_EXPIRED
16. Confirm logout/subscription screen
```

ثم نفس الاختبار في:

```text
Cloud Mode
```

مع التحقق من أن البيانات لا تمر عبر SQLite.


```text
      ↓
Final Logout / Subscription Expired
```

## الخلاصة التنفيذية للمطور

لا نريد Patch جديدًا يعالج عرضًا واحدًا.

نريد مراجعة **Authentication + Connection Mode + Subscription Verification + Refresh + Sync** كمنظومة واحدة، وإزالة جميع المسارات التي يمكن أن تسبب Logout بسبب أخطاء مؤقتة.

الأولوية:

1. فصل Local وCloud بشكل كامل.
2. إصلاح Pre-login Connection Selection.
3. حماية Refresh Token باستخدام HttpOnly Secure Cookie.
4. إصلاح Refresh Token Race.
5. جعل Subscription Service هي المصدر النهائي لحالة الاشتراك.
6. عدم الاعتماد على وقت الجهاز.
7. عدم تنفيذ Logout بسبب 401/500/502/503/504 أو أخطاء الشبكة المؤقتة.
8. جعل `SUBSCRIPTION_EXPIRED` Error Code صريحًا وحيدًا لانتهاء الاشتراك.
9. إصلاح Local → Cloud Sync.
10. إصلاح Cloud → Local Sync.
11. منع تكرار عمليات المزامنة.
12. تنفيذ اختبارات E2E كاملة في Local وCloud.
13. عدم اعتبار العمل منتهيًا بمجرد نجاح `200 OK`؛ يجب إثبات أن البيانات وصلت إلى قاعدة البيانات الصحيحة وأن المسار الصحيح استُخدم.
14. عدم تغيير Business Logic أو الواجهة إلا إذا كان ذلك ضروريًا للإصلاح.

**المعيار النهائي:**

> المستخدم يجب ألا يُطرد من النظام بسبب خطأ تقني مؤقت. يجب أن يبقى داخل الجلسة ويتم الإصلاح/إعادة المحاولة تلقائيًا. إنهاء الجلسة تلقائيًا لا يحدث إلا بعد إثبات السبب النهائي المسموح به، وعلى رأسه انتهاء الاشتراك الحقيقي، أو حالة انقطاع اتصال فعلية وفق سياسة النظام.
