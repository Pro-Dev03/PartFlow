# سياسة الأمان وتحديثات PartFlow

**تاريخ التقرير:** 2026-09-25

**الفرع:** `main`؛ يشمل التقرير إصلاح الوردية وحصر اختيار Electron في المحلي.

**نطاق النشر:** واجهة Render، وAPI على Render، وقاعدة PostgreSQL/Supabase واحدة لمتجر واحد.

## السياسة المعتمدة

الخادم السحابي هو المرجع الموثوق للمستخدمين والاشتراكات وصلاحية العمليات. واجهة الويب أو نسخة Electron أو قاعدة SQLite المحلية لا تمنح اشتراكًا ولا تقرر صلاحية البيع والمخزون. يرسل التطبيق طلبات العمل إلى API السحابي في وضعي الاتصال المحلي والسحابي؛ المقصود بالوضع المحلي هو تشغيل التطبيق/خدمة الجهاز، وليس السماح بمتابعة العمل التجاري دون تحقق سحابي.

اعتمد المشروع حاليًا متجرًا واحدًا وقاعدة سحابية واحدة. لم يُفعّل عزل متعدد المتاجر أو سياسات RLS لكل متجر. لذلك لا يجوز اعتبار `080_tenant_isolation.sql` جزءًا من الترحيلات المطلوبة لهذا النشر. إذا أضيفت متاجر متعددة مستقبلًا، يجب تصميم عزل كامل واختباره قبل استقبال بياناتها في قاعدة مشتركة.

## ما تم تحديثه

### المصادقة والاشتراك

- التسجيل العام مغلق، ولا ينبغي أن ينشئ مسار التسجيل حسابًا باشتراك نشط.
- يتحقق الخادم من حالة الحساب والاشتراك عند الطلبات المحمية، ويميز أسباب الرفض بأكواد مثل `SUBSCRIPTION_EXPIRED` و`SUBSCRIPTION_SUSPENDED` و`ACCOUNT_DELETED` و`ADMIN_REQUIRED`.
- يميز النظام تعذر التحقق أو تعطل الخدمة عن رفض الاشتراك. عند تعذر التحقق من صلاحية السحابة، لا يسمح بتنفيذ عمليات العمل.
- تغيير كلمة المرور وإعادة تعيينها يزيدان `session_version` ويبطلان جلسات الوصول القديمة، ويحذفان رموز التجديد ضمن معاملة. تسجيل الخروج يبطل جلسات الوصول ورموز التجديد على الخادم.
- التعليق أو حذف المشترك يبطل رموز التجديد؛ كما يمنع فحص الحساب والاشتراك الطلبات المحمية حتى لو بقي لدى العميل Access Token.
- تخزين Refresh Tokens إلزامي. إذا كان جدول `refresh_tokens` مفقودًا أو تعذر استخدامه، تفشل عمليات الدخول أو التجديد أو الإبطال المعنية برسالة خطأ بدل الادعاء بأن الجلسة أُبطلت. يجب أن تكون الترحيلات اللازمة مطبقة على قاعدة الإنتاج.
- رموز الوصول قصيرة العمر، وتُدار رموز التجديد على الخادم مع تدوير الرمز عند التجديد. تغييرات الجلسة تمنع إعادة استخدام الرموز القديمة.
- مسار Supabase Auth غير مكتمل ومرفوض عند التهيئة؛ لا تضبط `USE_SUPABASE_AUTH=true` حاليًا.

### الاتصال المحلي، انقطاع الإنترنت، والمنح غير المتصلة

- طلبات العمل في التطبيق المحلي تتطلب قرار صلاحية حيًا من API السحابي. لا تُستخدم Offline Grant أو مهلة 72 ساعة لتفويض العمل.
- إذا تعذر الوصول إلى السحابة، تُقفل عمليات العمل المحمية ويُنهى سياق الجلسة/التحقق، بدل الاعتماد على نتيجة قديمة أو ساعة الجهاز.
- هذا يمنع استخدام انقطاع الشبكة كطريقة للاستمرار بعد انتهاء الاشتراك أو تعليقه، لكنه يعني أن العمل التجاري يتوقف عند انقطاع الإنترنت.
- لا يستطيع النظام إيصال إبطال فوري إلى جهاز غير متصل. عند عودة الاتصال، يرفض الخادم الطلبات وفق حالة الحساب الحالية. تسجيل الخروج دون شبكة ينظف بيانات الجلسة المحلية، لكنه لا يضمن وصول طلب الإبطال إلى الخادم قبل عودة الاتصال.
- لا توجد حماية برمجية كاملة من مالك الجهاز الذي يتحكم بنظام التشغيل أو يستطيع تعديل البرنامج أو قاعدة بياناته المحلية. الهدف الأمني هو أن النسخة المعدلة لا تستطيع اكتساب صلاحية على بيانات وخدمات الخادم دون اجتياز فحوص الخادم. أي بيانات تُخزّن محليًا تبقى ضمن سيطرة مالك الجهاز.

### بيانات العمل والسحابة

- المبيعات والمخزون وطلبات العمل موجهة إلى API Render في وضعي التشغيل، ويظل الخادم هو من يطبق المصادقة والاشتراك والصلاحيات.
- تسمح التحديثات للمشترك باستخدام مزامنة المتجر ورفع/تنزيل بيانات المتجر وفق المسارات المصرح بها. إعدادات قواعد البيانات الحساسة وأدوات إدارتها تبقى محصورة بالإدارة.
- تحديثات جلسة السحابة تتعامل مع أخطاء التحقق وأخطاء الخدمة بشكل أوضح، وتحافظ على قفل العمل عند فشل تحقق السحابة.
- عولج سلوك أخطاء API الذي كان قد يخرج المستخدم تلقائيًا بسبب خطأ عمل عابر مثل فشل تحميل الوردية (HTTP 500). فشل نقطة أعمال لا يُعامل وحده كإبطال مصادقة؛ أما رفض المصادقة/الاشتراك الصريح فيظل سببًا للقفل أو تسجيل الخروج.
- عنوان API في الواجهة مضبوط على الخدمة المعتمدة ولا يُؤخذ من قيمة يختارها العميل في `localStorage`.

### قاعدة Supabase وتهيئة الاتصال

- أُضيف الترحيل `081_single_store_cloud_hardening.sql` لتقوية توافق مخطط قاعدة المتجر الواحد، وتأمين بعض الـ views، وسحب صلاحيات الوصول المباشر غير اللازمة من أدوار Supabase العامة، وتثبيت `search_path` للدوال المحددة.
- أُضيف الترحيل `082_remove_duplicate_indexes.sql` لإزالة الفهارس المتطابقة التي أبلغ عنها Supabase مع الإبقاء على فهرس واحد لكل مجموعة.
- أفاد مالك المشروع بأن ترحيلي 081 و082 نُفذا بنجاح في قاعدة Supabase. ينبغي الاحتفاظ بنسخة احتياطية وسجل الترحيلات كمرجع تشغيلي.
- بيانات اتصال PostgreSQL ومفاتيح الإدارة يجب أن تبقى في أسرار بيئة Render الخلفية، ولا توضع في كود الواجهة أو حزمة Electron. لا تستخدم مفتاح `service_role` في العميل.
- إعداد CORS الإنتاجي يجب أن يحصر الأصول في عناوين الموقع المنشورة وأصل Electron المعتمد `partflow://app`. يجب عدم السماح بـ `*` أو الأصل المبهم `null` في الإنتاج.

## الترحيلات ذات الصلة

| الترحيل | الغرض | الحالة حسب المعلومات المتاحة |
| --- | --- | --- |
| `054_refresh_token_revocation.sql` | تخزين Refresh Tokens لإدارتها وإبطالها | مطلوب للمصادقة الآمنة؛ يجب أن يكون مطبقًا على قاعدة الإنتاج |
| `081_single_store_cloud_hardening.sql` | تقوية مخطط Supabase الحالي لمتجر واحد | أفاد المستخدم بنجاح التنفيذ |
| `082_remove_duplicate_indexes.sql` | حذف الفهارس المتطابقة التي أظهرها فاحص Supabase | أفاد المستخدم بنجاح التنفيذ |
| `083_access_session_version.sql` | إضافة `users.session_version` لإبطال Access JWT فورًا عند الخروج أو تغيير كلمة المرور | أضيف بعد ترحيلي 081/082؛ يجب تطبيقه قبل نشر الإصدار الذي يستخدم إبطال الجلسات الفوري |
| `080_tenant_isolation.sql` | عزل عدة متاجر بواسطة tenant/RLS | غير معتمد في سياسة المتجر الواحد الحالية؛ لا تنفذه ضمن هذا الإعداد |

**إجراء قاعدة البيانات المتبقي:** نجاح 081 و082 لا يشمل 083. طبّق ملف `backend/migrations/083_access_session_version.sql` مرة واحدة على قاعدة Supabase الإنتاجية بعد نسخة احتياطية، ثم تحقق من وجود العمود `users.session_version`. بدونه قد تفشل المصادقة أو لا يعمل الإبطال الفوري للجلسات كما هو مقصود في الإصدار الأخير.

## سجل العمل الذي غطته هذه المراجعة

- **اعتماد المتجر الواحد:** عُدِل مسار العمل ليستخدم قاعدة سحابية واحدة لمتجر واحد بدل بدء تطبيق عزل متعدد المتاجر. بقيت آليات tenant/RLS القديمة خارج مسار التشغيل المعتمد، كما أُضيفت حماية لمخطط Supabase الحالي بدل فرض ترحيل RLS جديد.
- **الانتقال من SQLite كمرجع للصلاحية:** اختيرت Render API لتنفيذ عمليات المتجر والتحقق من الاشتراك، حتى عند تشغيل البرنامج المكتبي أو اختيار وضع الاتصال المحلي. تظل قاعدة SQLite لأغراض الجهاز والمزامنة/النسخة المحلية، وليست مصدر قرار التفويض السحابي.
- **تدفق البيانات للمشترك:** أتيح للمشترك استخدام مزامنة بيانات متجره ورفعها وتنزيلها عبر المسارات المصرح بها. إعدادات قاعدة البيانات والأدوات الإدارية الحساسة تبقى إدارية.
- **اختلاف واجهة الدخول بحسب المنصة:** نسخة الويب تحتفظ بخياري الاتصال. حزمة Electron تعرض الاتصال المحلي فقط وتفرضه حتى لو كانت نسخة أقدم قد حفظت اختيار «سحابي». هذا تغيير في اختيار اتصال الجهاز فقط: عمليات المتجر في Electron تظل على Render وتظل خاضعة لمصادقة السحابة والاشتراك كما كانت.
- **استمرار الجلسة عند العطل التقني:** لا ينبغي تسجيل خروج المستخدم بسبب HTTP 500 من عملية متجر مثل تحميل الوردية أو بسبب تعطل مؤقت. يبقى فحص الحساب والاشتراك في الخادم، وتُوجّه الأكواد الصريحة لانتهاء/تعليق/حذف الحساب إلى صفحة انتهاء الاشتراك. تعطيل هذا الفحص نفسه سيمنع الطرد الفوري، لذلك لم يُعطل.
- **إصلاحات الاتصال والمتصفح:** عولجت أخطاء تشغيل الموقع وطلبات API السحابية، وتوافق واجهة الويب وElectron وCORS. رُفضت إعدادات CORS الخطرة مثل `null` و`*` في الإنتاج، وأزيل اعتماد العميل على اختيار عنوان API محفوظ.
- **مشاكل العمل والمصادقة:** عولجت أخطاء توافق استعلامات السحابة التي أثرت في المخزون والتقارير وبعض الشاشات، ومن ضمنها تحميل الوردية. عُدّل العميل كي لا يحول كل خطأ أعمال HTTP 500 تلقائيًا إلى تسجيل خروج، مع الإبقاء على قفل الجلسة عند فشل التحقق من الاشتراك أو الحساب.
- **متابعة عطل الوردية الحالي:** أضيف إصلاح لتهيئة `pos_shifts` عند بدء API: إذا كان الجدول موجودًا من إصدار قديم بأعمدة ناقصة، تُضاف الأعمدة المطلوبة بدل أن يظل `CREATE TABLE IF NOT EXISTS` يترك المخطط القديم كما هو. كما أصبحت مقارنة `user_id` تتعامل مع PostgreSQL UUID وTEXT. اختبار انحدار بجدول قديم يؤكد أن المسار يعمل محليًا ويحافظ على السجل، لكن التحقق الحي بعد الدفع ما زال يعيد 500؛ لا نعتبر إصلاح الإنتاج مكتملًا قبل تحديد خطأ Render الفعلي.
- **الجلسات وكلمات المرور:** أضيف ربط JWT بـ `session_version`، وإبطاله عند Logout وتغيير/إعادة تعيين كلمة المرور، مع حذف Refresh Tokens. تُبطل رموز التجديد كذلك عند تعطيل/تعليق الحساب أو حذفه من مسارات الإدارة ذات الصلة.
- **واجهة الدخول:** حُدثت بصريًا شاشة الدخول وطريقة اختيار الاتصال ورسائل الأخطاء. التغييرات الشكلية لا تشكل بحد ذاتها حاجزًا أمنيًا؛ الحماية تأتي من فحوص الخادم.
- **قاعدة البيانات:** أضيفت تحسينات Supabase لمخطط المتجر الواحد، وأزيلت الفهارس المتطابقة التي أظهرها فاحص Supabase. المستخدم أكد نجاح ترحيلي 081 و082، ثم أضيف الترحيل 083 بعد ذلك.
- **إصلاحات تشغيلية أخرى:** عولج توافق تقارير السحابة وبعض استعلامات المخزون، ومشاكل استيراد/مزامنة البيانات وبعض سيناريوهات التعامل مع السجلات المحذوفة تاريخيًا، بحسب commits الموجودة على `main`.

## التحقق والنتائج

سجل التحقق السابق للمشروع نجاح اختبارات مركزة في حزم المصادقة وmiddleware والمستخدمين وAPI والإعدادات والمزامنة، واختبارات الواجهة المتعلقة بـ `authStore` وعميل API، إضافة إلى فحص بناء الواجهة وملفات Electron. تشمل الاختبارات حالات تغيير كلمة المرور وإبطال الجلسات، غياب جدول Refresh Tokens، تعليق الاشتراك، رفض التسجيل العام، فشل تحقق السحابة، ورفض إعداد CORS غير الآمن.

وجود الكود على `origin/main` ونجاح ترحيل SQL لا يثبتان وحدهما أن Render يشغّل آخر إصدار أو أن كل متغيرات الإنتاج مضبوطة كما ينبغي. لا يتضمن هذا التقرير فحصًا حيًا جديدًا للخدمات. قبل اعتماد الحماية على الموقع، تحقق من اكتمال آخر Deploy في Render، وسجلات بدء التشغيل، و`CORS_ALLOWED_ORIGINS`، وقيم اتصال قاعدة البيانات وأسرار JWT، ثم اختبر دخولًا وبيعًا ومخزونًا وتغيير كلمة مرور وتعليق حساب على الخدمة الحية.

في اختبار حي بحساب الاختبار، أعاد تسجيل الدخول 200، كما أعاد `/users/me` و`/dashboard/stats` حالة 200، لكن `/sales/shifts/current` أعاد 500. أعاد `/health` حالة 200 وقاعدة البيانات `healthy`، وأعاد طلب الوردية بلا Authorization حالة 401 كما يتوقع endpoint محمي. هذا يعزل العطل إلى مسار الوردية، ويثبت أن 401 في اختبار بلا رمز لا يمثل خطأ الجلسة. معرّف آخر طلب فاشل هو `eb96712c-7593-415d-ae6f-def31ed6702d`. إصلاح التوافق للجدول القديم اجتاز اختبارات SQLite/API محليًا ودُفع إلى GitHub، لكنه لم يثبت بعد إصلاح العطل على Render. يلزم فحص سجل API المطابق لمعرّف الطلب ورسالة قاعدة البيانات قبل اعتبار المشكلة محلولة؛ لا تُعطّل فحص الاشتراك أو تعِد تسمية 500 كخطأ مصادقة.

## الحدود والمخاطر المتبقية

1. **مالك الجهاز:** يستطيع مالك جهاز مخترق تعديل برنامجه أو SQLite وقراءة أي بيانات محلية. حماية الاشتراك تمنع هذه التعديلات من منح صلاحية خادم، بشرط أن تكون كل البيانات والقرارات الحساسة فعلًا على الخادم.
2. **العمل دون إنترنت:** السياسة الحالية تتطلب الاتصال للخدمات المحمية؛ لا يوجد تشغيل أوفلاين لمدة 72 ساعة. أثناء الانقطاع لن يُعتمد على ساعة الجهاز لتجديد السماح.
3. **إبطال الجلسة دون اتصال:** لا يمكن ضمان وصول Logout للسحابة إذا كان الجهاز غير متصل. رمز الوصول الموجود يظل محكومًا بانتهائه وبفحوص الخادم عند اتصاله.
4. **متجر واحد:** لا توجد حدود بيانات متعددة المستأجرين في الإعداد الحالي. إضافة متجر ثانٍ إلى قاعدة البيانات نفسها قبل تطبيق واختبار تصميم عزل كامل تنشئ خطر كشف أو خلط البيانات.
5. **النشر:** يلزم التأكد من أن API والموقع المنشورين يطابقان commit الحالي، لأن فحص صحة الخدمة أو نجاح صفحة الدخول لا يكفي لإثبات نشر إصلاحات المصادقة.
6. **الاعتماد على المتصفح:** XSS أو برمجية خبيثة أو سرقة جهاز المستخدم قد تكشف رموز الجلسة أو بياناته. يجب الاستمرار في تقليل تخزين الأسرار، وتحديث Electron، وحماية الحسابات وكلمات المرور، وعدم تسجيل الرموز في السجلات.

## قائمة تحقق النشر

- [ ] تأكيد أن Render نشر أحدث commit من `main`، بما فيه إصلاح ترقية مخطط `pos_shifts`.
- [ ] التحقق من أسرار Render دون نسخها إلى المحادثات أو الملفات: `DATABASE_URL`، ومفتاح JWT، وعنوان Cloud API، و`CORS_ALLOWED_ORIGINS`.
- [ ] التأكد من أن `CORS_ALLOWED_ORIGINS` يتضمن الأصول الصحيحة للموقع و`partflow://app` ولا يتضمن `*` أو `null`.
- [ ] التأكد من تطبيق مخطط Refresh Tokens وترحيلات المستخدمين اللازمة على قاعدة الإنتاج.
- [ ] اختبار انتهاء الاشتراك وتعليقه: يجب أن يرفض الخادم عمليات الأعمال ويعيد سببًا واضحًا.
- [ ] اختبار تغيير كلمة المرور: يجب رفض Access Token القديم وRefresh Token القديم.
- [ ] اختبار انقطاع API: يجب ألا تنجح عمليات الأعمال المحمية دون تحقق حي.
- [ ] اختبار البيع والمخزون والوردية والمزامنة والرفع والتنزيل بحساب مشترك، والتأكد من بقاء إعدادات الإدارة الحساسة محمية.
- [ ] التحقق من نسخة احتياطية حديثة لـ Supabase وخطة استعادة قبل أي ترحيل مستقبلي.
