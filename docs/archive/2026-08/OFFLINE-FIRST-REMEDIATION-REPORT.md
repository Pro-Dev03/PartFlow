# تقرير معالجة الاتصال: اعتماد Offline-first في PartFlow

**التاريخ:** 2026-08-30  
**الحالة:** خطة معالجة قبل اعتماد التشغيل التجاري متعدد الأجهزة  
**القرار المعماري:** التطبيق المحلي (Electron + Go API + SQLite) هو بيئة العمل الأساسية. السحابة هي النسخة الاحتياطية، إدارة الاشتراكات، والمزامنة بين الأجهزة؛ وليست شرطاً لإتمام البيع اليومي.

---

## 1. الملخص التنفيذي

بما أن معظم عمل المتجر سيكون دون إنترنت، يجب أن يصبح PartFlow نظاماً **محلياً أولاً**:

- كل عملية يومية مهمة (بيع، شراء، مخزون، عميل، دفعة، مرتجع) تُنفذ وتُحفظ في SQLite محلياً فوراً.
- لا يجوز أن يؤدي انقطاع الإنترنت إلى تحويل البيع إلى مسودة في المتصفح فقط أو إلى منع صاحب المتجر من إكمال عمله.
- كل تغيير محلي يُسجل، في نفس المعاملة، داخل طابور مزامنة دائم في SQLite.
- عند عودة الشبكة، تُرسل العمليات إلى السحابة بطريقة آمنة وقابلة لإعادة المحاولة، ثم تُنزّل التغييرات القادمة من السحابة.
- السحابة هي مصدر الحقيقة المشتركة بين الأجهزة وإدارة الاشتراك، لكن الجهاز المحلي يظل قادراً على العمل ضمن سياسة ترخيص أوفلاين واضحة.

الوضع الحالي يحتوي على عناصر مفيدة: SQLite محلي، Electron، جدول `sync_queue`، هيكل مزامنة، وحارس اشتراك محلي. لكنه لا يحقق التدفق أعلاه بشكل متسق. لذلك لا ينبغي وصف المنتج حالياً بأنه يدعم «مزامنة Offline/Online مكتملة» قبل تنفيذ هذه الخطة.

## 2. الوضع الحالي والمشكلات المؤكدة

### 2.1 عدم وجود مصدر واحد للعمليات المعلقة

يوجد طابوران مستقلان:

| المكان | الآلية الحالية | المشكلة |
|---|---|---|
| المتصفح | `localStorage` باسم `offline_queue` | لا يضمن حفظاً تجارياً دائماً، ولا يرتبط بطابور الخادم المحلي |
| SQLite المحلي | جدول `sync_queue` | موجود، لكن أغلب عمليات النظام لا تضيف إليه سجلات |

النتيجة: قد يظن المستخدم أن عملية بيع حُفظت، بينما هي مسودة في المتصفح وليست بيعاً محاسبياً ولا حركة مخزون محلية قابلة للمزامنة.

### 2.2 سلوك POS عند انقطاع الشبكة

في صفحة POS، تُعامل حالة `navigator.onLine === false` على أنها سبب لحفظ بعض الإجراءات في طابور المتصفح. بينما تطبيق Electron لديه API محلي على `localhost` يجب أن يبقى متاحاً حتى بدون إنترنت.

النتيجة المطلوبة هي:

```text
انقطاع الإنترنت
    ↓
POS يطلب API المحلي
    ↓
SQLite يسجل البيع + العناصر + حركة المخزون + الدفعة/الدين + حدث المزامنة
    ↓
إيصال فوري وحالة «بانتظار المزامنة»
```

وليس:

```text
انقطاع الإنترنت → localStorage → محاولة رفع لاحقة غير مضمونة
```

### 2.3 تبديل Offline/Online لا يمثل مزامنة حقيقية

الواجهة تغيّر عنوان الـAPI بين المحلي والسحابي. في المقابل، تطبيق Desktop يشغّل الخادم المضمّن دائماً على SQLite محلي. لذلك لا يوجد جسر موثوق يحقق:

- تنزيل نسخة حديثة من السحابة قبل العمل المحلي.
- إرسال كل التغييرات المحلية إلى السحابة.
- تنزيل تغييرات السحابة بعد الإرسال.
- توحيد البيانات بين جهازين.

يجب عدم استخدام اختيار المستخدم «أوفلاين/أونلاين» لتحديد مكان كتابة البيانات. مكان الكتابة في Desktop يجب أن يكون محلياً دائماً؛ الاتصال يحدد فقط ما إذا كانت المزامنة ممكنة الآن.

### 2.4 عامل المزامنة غير مضمون في نسخة سطح المكتب

عامل المزامنة موجود في `backend/cmd/worker`، لكن Electron يشغّل API المحلي وليس العامل. وبالتالي لا توجد مزامنة دورية مؤكدة في نسخة العميل.

### 2.5 تعارضات المزامنة غير مكتملة

التعارض يُسجل، لكن اختيار سياسة مثل `server_wins` أو `client_wins` لا يطبق المعالجة على البيانات نفسها؛ يحذف سجل التعارض فقط. كما أن مزامنة السجلات المالية عبر upsert عام قد تضر بمبدأ السجل غير القابل للحذف أو التعديل.

### 2.6 وضع PWA غير موثوق كحل أوفلاين

تسجيل Service Worker معطّل صراحة في `frontend/src/main.tsx`. إعداد Vite PWA موجود لكنه مشروط بمتغير بيئة، لذلك لا ينبغي الاعتماد على PWA كبديل لتطبيق Desktop المحلي أو الادعاء بدعمه دون اختبار إنتاجي مستقل.

### 2.7 الاشتراك المحلي قابل للتلاعب

حالة الاشتراك وفترة السماح تحفظ في `localStorage` وSQLite على جهاز العميل. هذا مقبول لتحسين التجربة فقط، وليس كسند أمني نهائي؛ مستخدم لديه تحكم بالجهاز يمكنه تعديل التخزين المحلي أو ساعة النظام. كذلك إنشاء مالك محلي بكلمة مرور ثابتة في قاعدة جديدة خطر أمني يجب إزالته قبل التوزيع.

## 3. النموذج المستهدف

### 3.1 فصل ثلاثة مفاهيم

| المفهوم | المعنى | مصدره |
|---|---|---|
| قاعدة العمل | مكان تنفيذ وحفظ العمل اليومي | SQLite المحلي دائماً في Desktop |
| حالة الاتصال | هل يمكن الوصول إلى السحابة الآن؟ | فحص فعلي للـAPI السحابي، لا `navigator.onLine` فقط |
| المزامنة | تبادل التغييرات بين المحلي والسحابي | خدمة Sync محددة وصريحة |

لا ينبغي أن يؤدي تغيّر حالة الاتصال وحده إلى تبديل مستودع البيانات التشغيلي أو خسارة الوظائف المحلية.

### 3.2 تدفق البيانات المستهدف

```text
واجهة Electron / React
        │ HTTP: localhost فقط
        ▼
Go Local API
        │ معاملة SQLite واحدة
        ├── بيانات العمل: sale / payment / inventory movement / ...
        ├── سجل تدقيق immutable event
        └── outbox: sync_queue
        │
        ▼ عند توفر الشبكة
Sync Agent
        ├── Push: يرسل أحداث outbox إلى Cloud Sync API
        └── Pull: ينزّل أحداث السحابة منذ cursor آخر
        ▼
Cloud API + PostgreSQL
```

في المتصفح العادي يمكن استخدام API السحابي مباشرة كنسخة Online-only، أو بناء طبقة IndexedDB مستقلة لاحقاً. لا ينبغي خلط هذا السيناريو مع نسخة Electron المحلية في المرحلة الأولى.

### 3.3 قواعد جوهرية

1. كل Mutation تجاري يبدأ من API المحلي ويُنفذ في SQLite.
2. كل Mutation يكتب سجل outbox في نفس transaction؛ نجاح العملية لا يعتمد على الإنترنت.
3. كل حدث يملك `event_id` و`device_id` و`idempotency_key` فريدة.
4. الخادم السحابي يقبل الحدث مرة واحدة فقط؛ إعادة الإرسال آمنة.
5. السجلات المالية والمخزون لا تُحذف ولا تُعدل مباشرة بعد الاعتماد؛ تُعكس بأحداث عكسية.
6. المزامنة لا تستخدم `SELECT *` ولا upsert عاماً لكل الجداول.
7. يجب ألا يظهر للمستخدم وضع تقني غامض؛ تظهر حالة عمل بسيطة: «محفوظ محلياً»، «بانتظار المزامنة»، «تمت المزامنة»، «يحتاج مراجعة».

## 4. التصميم المقترح للمزامنة

### 4.1 نموذج Event/Outbox بدلاً من نسخ الصفوف العامة

استخدام upsert لأي صف يصلح للبيانات المرجعية البسيطة فقط، ولا يصلح للبيع والدفعات وحركات المخزون. البديل هو تسجيل أحداث مجال العمل.

أمثلة أحداث:

| المجال | الحدث |
|---|---|
| المبيعات | `sale.completed`, `sale.cancelled`, `sale.payment_recorded` |
| المخزون | `inventory.received`, `inventory.sold`, `inventory.adjusted`, `inventory.reversed` |
| العملاء | `customer.created`, `customer.updated` |
| المشتريات | `purchase.received`, `purchase.reversed` |
| المدفوعات | `payment.recorded`, `payment.reversed` |
| الاشتراك | `license.validated`, `license.revoked` |

### 4.2 توسيع جدول outbox المحلي

تطوير `sync_queue` أو استبداله بجدول `sync_outbox` يتضمن:

```sql
event_id            TEXT PRIMARY KEY
device_id           TEXT NOT NULL
store_id            TEXT NOT NULL
aggregate_type      TEXT NOT NULL
aggregate_id        TEXT NOT NULL
event_type          TEXT NOT NULL
payload             TEXT NOT NULL
occurred_at         TEXT NOT NULL
schema_version      INTEGER NOT NULL DEFAULT 1
idempotency_key     TEXT NOT NULL UNIQUE
sync_status         TEXT NOT NULL DEFAULT 'pending'
attempts            INTEGER NOT NULL DEFAULT 0
next_retry_at       TEXT
last_error          TEXT
synced_at           TEXT
```

والجدول السحابي المقابل يحفظ `event_id` و`device_id` و`idempotency_key` فريدة. يجب أن يعيد الخادم نجاحاً للحادثة المكررة نفسها بدلاً من إنشاء أثر ثانٍ.

### 4.3 نقاط API المطلوبة

```text
POST /api/v1/sync/push
  الطلب: device_id, store_id, events[]
  الرد: accepted_event_ids[], rejected[], server_cursor

GET /api/v1/sync/pull?cursor=...
  الرد: events[], next_cursor, has_more

POST /api/v1/sync/bootstrap
  الاستخدام: جهاز جديد أو إعادة بناء قاعدة محلية
  الرد: snapshot موقّع ومقسّم إلى صفحات

POST /api/v1/license/validate
  الرد: license token موقّع، last_validated_at، policy
```

يجب أن تكون هذه المسارات خاصة بالمزامنة، لا أن تعتمد على تشغيل API محلي يحمل اتصال PostgreSQL مباشراً.

### 4.4 ترتيب المزامنة

1. التأكد من صحة الجلسة والرخصة عند توفر الشبكة.
2. رفع outbox على دفعات، بترتيب زمني لكل `aggregate_id`.
3. تعليم الأحداث المقبولة بأنها synced محلياً.
4. تنزيل الأحداث السحابية من آخر cursor.
5. تطبيقها محلياً ضمن معاملات SQLite، وحفظ cursor الجديد.
6. إعادة حساب المجاميع/الكاش محلياً عند الحاجة.
7. إظهار نتيجة مختصرة وواضحة للمستخدم.

المشغّل يبدأ عند فتح التطبيق، وعند عودة الشبكة، وبعد أي عملية محلية ضمن debounce قصير، وكل عدة دقائق عند وجود طابور معلق. يبقى زر «مزامنة الآن» متاحاً، لكنه ليس الآلية الوحيدة.

## 5. سياسة التعارضات

### 5.1 لا سياسة موحدة لكل الأنواع

| نوع البيانات | السياسة الصحيحة |
|---|---|
| بيع، دفعة، حركة مخزون، مرتجع | append-only؛ لا دمج صامت ولا حذف |
| اسم العميل، هاتفه، بيانات غير مالية | نسخة أحدث مع حفظ audit، أو شاشة دمج عند تضارب مهم |
| إعدادات المتجر | server-wins مع إشعار، إلا إن كانت خاصة بالجهاز |
| كمية مخزون | تُشتق من الحركات؛ لا تُزامن كرقم نهائي مستقل |
| كتالوج المنتجات | revision/version مع مراجعة عند تعديل نفس الحقل |

### 5.2 تجربة المستخدم عند التعارض

- لا تحذف سجل التعارض عند اختيار سياسة قبل تطبيقها والتحقق منها.
- اعرض: السجل، قيمته المحلية، قيمته السحابية، الوقت، الجهاز الذي أنشأ التغيير، والأثر المتوقع.
- للتعارض المالي: لا تسمح بالدمج اليدوي للرقم؛ أنشئ عملية تصحيح/عكس صريحة.
- احتفظ بكل قرارات الحل في audit log.

## 6. الاشتراك والترخيص في بيئة Offline-first

### 6.1 السياسة الموصى بها

السحابة صاحبة القرار النهائي، لكن التطبيق المحلي لا يتوقف فور انقطاع الإنترنت.

#### سياسة PartFlow التشغيلية المعتمدة

- يُنشأ حساب المشترك ويُدار من الخادم السحابي فقط.
- مدة الاشتراك الاعتيادية هي **30 يوماً** من تاريخ التفعيل.
- مالك النظام يدير التجديد يدوياً؛ وعند عدم التجديد بعد انتهاء المدة، يحذف الحساب أو يعطّله يدوياً من السحابة.
- عند توفر الإنترنت، يجب أن يتحقق التطبيق من الخادم. إذا لم يعد الحساب موجوداً أو أصبح معطلاً، يُمنع الدخول أو الاستمرار فوراً.
- عند انقطاع الإنترنت، يسمح للتطبيق المحلي بالعمل فقط إذا كان الحساب قد اجتاز تحققاً سحابياً سابقاً ولديه رخصة محلية صالحة.
- لا يمكن إيقاف جهاز معزول عن الإنترنت فور حذف حسابه من السحابة؛ لذلك تنتهي صلاحية العمل المحلي بعد فترة سماح قصيرة ومحددة، وتُطبق حالة الحذف فور أول اتصال ناجح لاحق.

| الحالة | السلوك |
|---|---|
| اتصال متاح والاشتراك صالح | تحديث رخصة محلية موقعة واستمرار العمل |
| اتصال غير متاح والرخصة المحلية صالحة | عمل كامل محلياً |
| انتهت مدة 30 يوماً أثناء الانقطاع | فترة سماح قصيرة ومحددة بعد آخر تحقق سحابي صالح |
| عودة الاتصال والحساب محذوف/معطل يدوياً | منع الدخول أو الاستمرار فوراً، وإيقاف المزامنة؛ لا حذف بيانات المتجر المحلية |
| رخصة محلية معدلة أو غير موقعة | منع العمل بعد فترة استرداد قصيرة أو وضع قراءة فقط |

### 6.2 التنفيذ الآمن نسبياً

1. بعد تحقق سحابي ناجح، يصدر الخادم License Token موقّعاً بمفتاح خاص.
2. يحتوي على: `store_id`، `device_id` أو سياسة ربط الجهاز، تاريخ الانتهاء، آخر تحقق، فترة السماح، والإصدار.
3. يحتوي التطبيق على المفتاح العام فقط ويتحقق من التوقيع محلياً.
4. تحفظ الرخصة في مخزن نظام التشغيل المشفّر إن أمكن، وليس في `localStorage` فقط.
5. يسجل التطبيق كشف رجوع ساعة النظام أو التلاعب الواضح، بدون معاقبة المستخدم بسبب خطأ وقت بسيط.
6. إلغاء الاشتراك في السحابة يظهر فور أول اتصال لاحق؛ لا توجد طريقة تقنية لإلغائه فوراً على جهاز معزول بالكامل.

### 6.3 إجراءات أمنية لازمة الآن

- حذف إنشاء المستخدم الافتراضي صاحب كلمة المرور الثابتة `Owner123456` في إصدار التوزيع.
- فرض معالج إعداد أولي لإنشاء مالك بكلمة مرور يحددها المستخدم.
- عدم تخزين refresh token غير المشفر في SQLite أو `localStorage`.
- عدم اعتبار قيمة محلية لحالة الاشتراك مصدراً موثوقاً من دون توقيع الخادم.

## 7. تعديلات مطلوبة في المكونات الحالية

### الواجهة الأمامية

- اجعل Electron يستخدم `localhost` دائماً للعمليات التجارية، سواء كانت الشبكة موجودة أم لا.
- أزل الاعتماد المباشر على `navigator.onLine` لتقرير حفظ العملية؛ استخدمه فقط لتشغيل/إيقاف sync agent وعرض الحالة.
- أزل `offline_queue` وPOS drafts كبديل للمعاملات؛ يمكن الإبقاء على «مسودة البيع» كميزة مستقلة غير محاسبية فقط.
- أضف مؤشر حالة دائم: آخر مزامنة، عدد العمليات المعلقة، وآخر خطأ قابل للإجراء.
- لا تستعمل Cache API أو Service Worker لتخزين ردود API المالية كمصدر حقيقة.

### الـAPI المحلي

- يجب أن تُنشأ الخدمات والمستودعات من SQLite المحلي في نسخة Desktop.
- كل Command تجاري يكتب بيانات المجال وحدث outbox داخل transaction واحدة.
- استبدل اختيار المستودع بناء على `operating_mode` بخيار تشغيل واضح عند بدء API المحلي: `LOCAL_DESKTOP` أو `CLOUD_SERVER`.
- لا تفتح قاعدة SQLite جانبية منفصلة عن قاعدة العمل الفعلية؛ يجب أن يستخدم API والـsync agent نفس المسار/الإعداد.

### الـAPI السحابي

- يبقى PostgreSQL المصدر المركزي للبيانات المشتركة.
- أضف واجهة Sync مخصصة مع مصادقة الجهاز والمتجر.
- طبّق idempotency على الخادم، وقيوداً فريدة على event IDs.
- طبّق الأحداث في معاملات قاعدة البيانات مع audit log.

### Electron

- شغّل sync agent ضمن عملية الـbackend المحلية أو كعملية جانبية مضبوطة، ولا تعتمد على Worker خارجي غير مشغّل.
- لا تعيد تشغيل الـbackend عند كل تغيير واجهة بين «أوفلاين/أونلاين»؛ بدلاً من ذلك حدّث حالة الاتصال للمزامنة فقط.
- خزن `device_id` ثابتاً لكل تثبيت، واسمح بإلغائه من لوحة الإدارة عند فقدان الجهاز.

**معيار القبول:** فصل الإنترنت، إتمام بيع نقدي، إغلاق التطبيق وتشغيله، ثم العثور على البيع والمخزون والإيصال محلياً كما هي.

### المرحلة 1: مزامنة رفع موثوقة

**الهدف:** رفع العمليات المحلية من جهاز واحد إلى السحابة دون تكرار.

- [ ] بناء `POST /sync/push` وتخزين الأحداث السحابية مع idempotency.
- [ ] تشغيل Sync Agent من Desktop.
- [ ] retries مع exponential backoff وسبب فشل مرئي.
- [ ] إضافة شاشة طابور بسيطة: العدد، آخر نجاح، وإعادة المحاولة.

**معيار القبول:** إنشاء 100 عملية محلية مع انقطاع متقطع، ثم الحصول على 100 عملية فقط في السحابة بدون تكرار أو فقد.

### المرحلة 2: تنزيل التغييرات وتهيئة جهاز جديد

**الهدف:** توحيد جهازين بأمان.

- [ ] بناء `bootstrap` مقسم إلى صفحات مع checksum.
- [ ] بناء `GET /sync/pull` باستخدام cursor دائم.
- [ ] تطبيق الأحداث القادمة بصورة idempotent في SQLite.
- [ ] إضافة `device_id` و`store_id` وواجهة إدارة الأجهزة.

**معيار القبول:** بيع على جهاز A، مزامنة، ثم ظهور البيع والمخزون الصحيحين في جهاز B دون نسخ يدوي للقاعدة.

### المرحلة 3: التعارضات والسجلات غير القابلة للتلاعب

- [ ] استبدال حل التعارض الصوري بتطبيق سياسة فعلية ومسجلة.
- [ ] جعل الماليات والمخزون append-only مع عمليات عكس.
- [ ] تقديم واجهة مراجعة للتعارضات غير المالية.

**معيار القبول:** تعديل عميل على جهازين، وإظهار تعارض قابل للحل؛ وإنشاء دفعتين متوازيتين دون فقد أو دمج رقمي غير صحيح.

### المرحلة 4: الترخيص والاستقرار التشغيلي

- [ ] إصدار License Token موقّع والتحقق منه محلياً.
- [ ] نقل الأسرار/الجلسات إلى مخزن آمن قدر الإمكان.
- [ ] اختيار فترة سماح صريحة وتوثيقها للمستخدم.
- [ ] مراقبة المركزية: أجهزة متأخرة في المزامنة، أخطاء sync، تعارضات، ونسخ احتياطية.

## 9. خطة الاختبار الإلزامية

### اختبارات الوحدة

- توليد event/outbox مع كل command تجاري.
- idempotency عند إعادة إرسال الحدث نفسه.
- retry وتأخير المحاولة.
- تطبيق أحداث pull مرتين دون تغيير مزدوج.
- التحقق من رخصة موقعة ومن الرخصة المنتهية.

### اختبارات التكامل

- SQLite محلي + Cloud API/PostgreSQL في بيئة اختبار.
- انقطاع الشبكة أثناء رفع دفعة من الأحداث ثم عودتها.
- فشل منتصف معاملة البيع: يجب rollback للبيانات وoutbox معاً.
- bootstrap لجهاز جديد ثم pull لاحق.
- تعارض تعديل بيانات عميل من جهازين.

### اختبارات E2E في Electron

1. افتح التطبيق دون إنترنت.
2. سجل دخولاً برخصة محلية صالحة.
3. أضف منتجاً/عميلاً وأكمل بيعاً نقدياً وديناً.
4. أعد تشغيل التطبيق بلا إنترنت وتحقق من كل البيانات.
5. أعد الإنترنت وتأكد من رفع الأحداث.
6. افتح جهازاً ثانياً وتأكد من وصول التغييرات.
7. ألغِ الاشتراك في السحابة، أعد الاتصال، وتأكد من تطبيق السياسة بدون حذف بيانات المتجر.

### مؤشرات قبول قبل الإطلاق

| المؤشر | الحد الأدنى |
|---|---|
| فقدان عملية بعد انقطاع الشبكة | صفر في اختبارات التحمل |
| تكرار حدث بسبب retry | صفر |
| زمن إتمام بيع محلي | لا يعتمد على السحابة |
| استعادة التطبيق بعد إغلاق مفاجئ | كل المعاملات المعتمدة موجودة |
| مزامنة 1,000 حدث | قابلة للاستئناف مع نتائج قابلة للتدقيق |
| كشف حالة المزامنة للمستخدم | مفهوم ومتاح من كل شاشة رئيسية |

## 10. قرارات يجب اتخاذها من مالك المنتج

1. **فترة السماح بعد آخر تحقق سحابي صالح:** بما أن الاشتراك يُدار يدوياً لمدة 30 يوماً ثم يُحذف أو يعطّل عند عدم التجديد، التوصية هي 3 أيام للتحكم الأقوى أو 7 أيام لمرونة أعلى للمتجر. يجب تثبيت قيمة واحدة في إعدادات الخادم وتطبيقها ضمن الرخصة الموقعة.
2. **هل سيسمح باستخدام أكثر من جهاز؟** إن كانت الإجابة نعم، فـ`store_id` و`device_id` وpull/push والتعارضات ليست اختيارية.
3. **هل المتصفح العادي منتج مدعوم فعلاً؟** إن لم يكن كذلك، ركز المرحلة الأولى على Electron ولا تخلط PWA في المسار المحاسبي.
4. **ما هي سياسة النسخ الاحتياطي؟** أوصي بنسخة SQLite محلية يومية مشفرة + رفع اختياري عند توفر الإنترنت، مع اختبار الاستعادة.

## 11. الخلاصة

الاختيار الصحيح لـPartFlow هو **Local Desktop First, Cloud Sync Second**. هذا يطابق واقع المتاجر: البيع يجب ألا يتوقف بسبب الراوتر أو الإنترنت، لكن البيانات يجب أن تصل للسحابة بأمان عند عودة الاتصال.

أول أولوية ليست إضافة مزيد من الشاشات أو تحسين زر التحويل بين Online وOffline؛ بل جعل كل عملية مالية ومخزنية محلية، ذرية، وقابلة للمزامنة. بعد ذلك تصبح السحابة طبقة قوة ونسخ احتياطي وإدارة، بدلاً من أن تكون نقطة فشل للعمل اليومي.
