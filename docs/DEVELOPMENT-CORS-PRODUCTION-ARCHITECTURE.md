# تقرير اتصال PartFlow بين التطوير والإنتاج

## 1. الملخص

تطبيق PartFlow سيعمل في بيئتين مختلفتين:

- بيئة تطوير محلية باستخدام Vite على `http://localhost:5174`.
- تطبيق Windows تنفيذي مغلف بصيغة `exe` للمشتركين.

إضافة `http://localhost:5174` إلى إعدادات CORS في Render مفيدة لبيئة التطوير واختبار تسجيل الدخول من المتصفح، لكنها ليست متطلبًا لتشغيل النسخة التنفيذية النهائية.

## 2. سبب فشل اختبار المتصفح

كانت الواجهة المحلية تحاول الاتصال مباشرة بخدمة Render:

```text
http://localhost:5174
        |
        v
https://partflow-api.onrender.com
```

المتصفح أرسل طلب CORS تمهيديًا من نوع `OPTIONS`. خدمة Render لم تكن تسمح بالمصدر `http://localhost:5174`، ولذلك منع المتصفح طلب تسجيل الدخول قبل أن تصل النتيجة إلى الواجهة.

هذا يفسر الفرق بين الاختبارين:

- PowerShell ينجح لأن CORS قيد يطبقه المتصفح فقط.
- المتصفح يفشل إذا لم يرجع Render ترويسة `Access-Control-Allow-Origin` المناسبة.

المشكلة ليست في قاعدة البيانات أو الحساب أو كلمة المرور.

## 3. إعداد التطوير

لتشغيل نسخة Vite محليًا، يجب ضبط متغير Render التالي:

```text
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://localhost:5174,http://localhost:5175,http://127.0.0.1:5173,http://127.0.0.1:5174,http://127.0.0.1:5175
```

بعد حفظ المتغير في Render يجب تنفيذ Deploy جديد، ثم إعادة تحميل صفحة المتصفح.

يجب استخدام عناوين أصلية كاملة، ومن دون شرطة مائلة في النهاية. مثلًا:

```text
http://localhost:5174
```

وليس:

```text
http://localhost:5174/
```

## 4. بنية الإنتاج بعد تغليف exe

النسخة التنفيذية لا تعتمد على دومين واجهة أو منفذ Vite:

```text
PartFlow.exe
       |
       | http://localhost:8080
       v
Backend المحلي
       |
       | اتصال خادم بخادم عبر HTTPS
       v
Render API + قاعدة البيانات السحابية
```

في هذه البنية:

- لا يحتاج المشترك إلى دومين واجهة.
- لا يعتمد التطبيق على `localhost:5174` بعد التغليف.
- لا يجب أن تتصل واجهة التطبيق مباشرة بـRender في النسخة النهائية.
- Backend المحلي هو نقطة الاتصال بين الواجهة وخدمة Render.
- يجب أن يبقى الإنترنت متاحًا للتحقق من الحساب والاشتراك.
- SQLite تستخدم للبيانات التشغيلية المحلية فقط.
- Render هو مصدر الحقيقة للهوية والاشتراك والصلاحيات.

## 5. الحل الدائم الموصى به

لمنع اعتماد الإنتاج على CORS الخاص بواجهة التطوير:

1. ترسل الواجهة بيانات الدخول إلى Backend المحلي على `localhost:8080`.
2. يرسل Backend المحلي طلب المصادقة إلى Render من الخادم إلى الخادم.
3. يعيد Backend المحلي نتيجة المصادقة إلى الواجهة.
4. يتحقق Backend المحلي من جلسة السحابة قبل الطلبات المحمية.
5. عند انتهاء الاشتراك أو فشل التحقق السحابي، يمنع Backend العمليات المحمية.

بهذا يصبح CORS مطلوبًا فقط لنسخة الويب أو التطوير، وليس كجزء من اعتماد تطبيق `exe`.

## 6. ملاحظات الأمان والتشغيل

- لا توضع بيانات اعتماد قاعدة البيانات داخل الواجهة أو التطبيق التنفيذي.
- لا تعتبر SQLite مصدرًا لصلاحية الاشتراك.
- لا يُسمح باستخدام جلسة محلية كبديل عن التحقق السحابي.
- يجب إضافة دومين الواجهة الحقيقي إلى CORS فقط عند نشر نسخة ويب.
- يجب إعادة الاختبار بعد كل تغيير في متغيرات Render، لأن تغيير الملف المحلي لا يغير الخدمة المنشورة حتى يتم Deploy.

## 7. نتيجة الاختبارات الحالية

تم التأكد من الآتي:

- قاعدة PostgreSQL السحابية متصلة بنجاح.
- نقطتا `/health` و`/ready` تعملان.
- تسجيل الدخول إلى Render ينجح من اتصال مباشر.
- فحص TypeScript وبناء الواجهة نجح عبر `npm run build:check`.
- فشل المتصفح كان بسبب عدم السماح بمصدر `http://localhost:5174` في CORS.

## الخلاصة

إضافة `http://localhost:5174` في Render حل صحيح ومناسب لمرحلة التطوير الحالية. أما الحل الإنتاجي الدائم لتطبيق Windows فهو تمرير المصادقة والتحقق من الاشتراك عبر Backend المحلي، مع إبقاء Render سلطة الحساب والاشتراك الوحيدة.
