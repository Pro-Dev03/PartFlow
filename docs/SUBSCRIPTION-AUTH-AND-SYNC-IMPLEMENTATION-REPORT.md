# تقرير تنفيذ المصادقة والمزامنة المحلية والسحابية

التاريخ: 2026-09-21
المشروع: PartFlow

## 1. الملخص التنفيذي

تم تحسين دورة المصادقة والمزامنة في PartFlow لتدعم التشغيل المحلي والسحابي مع الحفاظ على التحقق من الاشتراك.

أصبح النظام يدعم ما يلي:

- تسجيل الدخول السحابي عبر Render وSupabase من خلال API السحابي.
- تشغيل العمليات المحلية عبر SQLite عند اختيار الوضع المحلي.
- تشغيل العمليات السحابية عبر API السحابي عند اختيار الوضع السحابي.
- التحقق من الاشتراك قبل السماح بالعمليات المحمية.
- منع الخروج المفاجئ عند أخطاء الشبكة أو انتهاء Access Token القابل للتجديد.
- تسجيل الخروج فقط عند انتهاء الاشتراك المؤكد من خدمة الاشتراكات.
- مزامنة البيانات من السحابة إلى SQLite المحلية.
- رفع طابور التغييرات المحلية إلى السحابة.
- إظهار خيار المزامنة للمشترك النشط داخل الإعدادات.

## 2. أوضاع الاتصال

### الوضع المحلي

في الوضع المحلي:

- العمليات التجارية تستخدم API المحلي على `http://localhost:8080/api/v1`.
- البيانات التشغيلية تحفظ في SQLite المحلية.
- يتم إرسال Cloud Token إلى الخادم المحلي للتحقق من الحساب والاشتراك.
- لا يعتمد قرار صلاحية الاشتراك على بيانات SQLite وحدها.
- عند عدم وجود اتصال بالإنترنت تبقى الجلسة محفوظة في حالة تحقق معلّق، ولا يتم تسجيل الخروج تلقائيًا.

### الوضع السحابي

في الوضع السحابي:

- العمليات التجارية تستخدم API السحابي على Render.
- API السحابي يتصل بقاعدة Supabase.
- تسجيل الدخول والتحقق من الاشتراك يتمان عبر API السحابي.
- لا يتم استخدام SQLite المحلية كمصدر للعمليات السحابية.
- مزامنة جهاز المستخدم تمر عبر API المحلي عندما يكون الهدف هو قراءة أو رفع بيانات SQLite الموجودة على الجهاز.

## 3. التحقق من الاشتراك

### مصدر القرار

تم اعتماد خدمة الاشتراك السحابية كمصدر القرار النهائي لصلاحية الاشتراك.

يتم التحقق عبر:

```text
POST https://partflow-api.onrender.com/api/v1/auth/validate
```

مع إرسال:

- `Authorization: Bearer <cloud_token>`
- `X-PartFlow-Cloud-Token: <cloud_token>`

### عدم الاعتماد على ساعة الجهاز

تم إزالة مقارنة تاريخ انتهاء الاشتراك مع ساعة الجهاز المحلي من مسار الثقة في الخادم المحلي.

النتيجة:

- تغيير تاريخ أو توقيت جهاز المستخدم لا ينهي الاشتراك الصحيح.
- القرار يعتمد على نتيجة خدمة الاشتراك السحابية.
- تاريخ الانتهاء المعروض في الواجهة للعرض فقط.
- المنع النهائي يعتمد على استجابة الاشتراك الصريحة من الخادم.

### حالات انتهاء الاشتراك

يتم إنهاء الجلسة فقط عند وصول استجابة صريحة تحمل:

```text
SUBSCRIPTION_EXPIRED
```

أما الحالات التالية فلا تؤدي إلى تسجيل الخروج:

- خطأ `401` قابل للتجديد.
- فشل مؤقت في Render.
- انقطاع الإنترنت.
- عدم توفر Cloud Token مؤقتًا أثناء استعادة الجلسة.
- فشل مؤقت في التحقق.
- خطأ خدمة أو مهلة اتصال.

في هذه الحالات يتم وضع الجلسة في حالة:

```text
cloudVerificationPending = true
```

ثم تتم إعادة المحاولة لاحقًا.

## 4. معالجة التوكن وتجديد الجلسة

تم تحسين تجديد التوكن في `authStore` و`ApiClient`.

### التجديد

عند انتهاء Access Token:

1. يحاول النظام استخدام Refresh Token.
2. يتم تحديث Cloud Token وRefresh Token عند نجاح التجديد.
3. يتم إعادة محاولة الطلب الأصلي بالتوكن الجديد.
4. لا يتم تسجيل الخروج بسبب فشل مؤقت.

### منع تعارض النوافذ

تمت إضافة قفل محلي لتجديد Cloud Token بين نوافذ المتصفح:

```text
partflow-cloud-refresh-lock
```

هذا يمنع نافذتين من إرسال Refresh Token نفسه في الوقت ذاته، خصوصًا عندما تكون Refresh Tokens قابلة للتدوير.

## 6. مسار المزامنة

### تنزيل السحابة إلى SQLite

المسار المنطقي:

```text
Cloud API -> Local API -> SQLite
```

تتم العملية عبر:

```text
POST /api/v1/settings/sync
```

ويقوم الخادم المحلي بما يلي:

1. استقبال جلسة المستخدم المحلية وCloud Token.
2. تمرير بيانات المصادقة إلى الخادم السحابي.
3. جلب snapshot البيانات من السحابة.
4. حفظ البيانات في SQLite المحلية.
5. تسجيل وقت آخر مزامنة.
6. إعادة نتيجة المزامنة للواجهة.

### رفع التغييرات المحلية إلى السحابة

المسار الصحيح هو:

```text
SQLite المحلية -> Local API -> Cloud API -> Supabase
```

ويتم عبر:

```text
POST /api/v1/settings/sync/push
```

أهم إصلاح تم تنفيذه:

- في الوضع السحابي كان زر الرفع يرسل مباشرة إلى Render، ولذلك كان يقرأ طابور السحابة بدل طابور SQLite المحلية.
- تم تعديل الواجهة لتوجيه مزامنة الجهاز دائمًا إلى API المحلي.
- API المحلي يقرأ `sync_queue` من SQLite.
- بعد ذلك يرسل العمليات المقبولة إلى API السحابي.
- API السحابي يطبق العمليات على قاعدة Supabase.

هذا هو الفرق بين:

```text
Cloud API مباشرة: لا يرى طابور SQLite الموجود على الجهاز
```

و:

```text
Local API: يرى SQLite الجهاز ثم يرفع التغييرات إلى Cloud API
```

## 7. صلاحيات المزامنة

تم تعديل مسارات المزامنة بحيث يستطيع المشترك الموثّق ذو الاشتراك النشط استخدامها.

المسارات التي أصبحت متاحة للمشترك الموثّق:

```text
GET  /api/v1/sync/initial-data
POST /api/v1/sync/push
POST /api/v1/settings/sync
POST /api/v1/settings/sync/push
GET  /api/v1/settings/sync/conflicts
DELETE /api/v1/settings/sync/conflicts
POST /api/v1/settings/sync/conflicts/:id/resolve
```

أما العمليات الحساسة مثل:

- حذف قاعدة البيانات.
- إدارة المشتركين.
- تغيير الاشتراكات.
- العمليات الإدارية المدمرة.

فما زالت محمية بصلاحية الإدارة.

## 8. معنى `processed: 0`

عند نجاح الرفع وظهور:

```json
{
  "processed": 0,
  "failed": 0
}
```

فهذا لا يعني أن قاعدة البيانات المحلية فارغة.

المعنى هو:

- توجد بيانات محلية محفوظة بالفعل.
- لا توجد تغييرات جديدة غير مرفوعة داخل جدول `sync_queue`.
- الرفع لا يعيد رفع snapshot كامل في كل مرة.
- الرفع يرسل فقط عمليات الإنشاء أو التعديل أو الحذف المسجلة في طابور المزامنة.

أما تنزيل snapshot من السحابة فهو المسار الذي ينقل مجموعة البيانات إلى SQLite المحلية.

## 9. التحقق من البيانات المحلية

تم التحقق من وجود قاعدة SQLite فعلية في:

```text
C:\Users\Administrator\AppData\Roaming\PartFlow\data\partflow.db
```

وكان حجم الملف يقارب 1 MB.

تم إنشاء جلسة محلية رسمية من Cloud Token ثم اختبار API المحلي، وكانت النتائج:

| المورد | الحالة | العدد |
|---|---:|---:|
| العملاء | 200 | 4 |
| الديون | 200 | 3 |
| المنتجات | 200 | 0 |
| المبيعات | 200 | 0 |

هذا يثبت أن SQLite تحتوي على بيانات فعلية، وليست مجرد ملف فارغ.

## 13. ملاحظات مهمة

### المزامنة ليست رفع snapshot كامل عند كل ضغطة

الرفع يعتمد على طابور التغييرات، وهذا مقصود لتقليل المخاطر ومنع الكتابة فوق بيانات السحابة دون معرفة التغييرات.

### وجود بيانات محلية لا يعني وجود عمليات رفع معلقة

البيانات الموجودة في SQLite قد تكون ناتجة عن تنزيل سابق من السحابة. لكي يظهر رقم `processed` أكبر من صفر، يجب أن يسجل النظام تغييرًا محليًا جديدًا في `sync_queue`.

### التحقق من الاشتراك مستمر

حتى مع نجاح المزامنة، تبقى صلاحية الاشتراك مرتبطة بخدمة السحابة. لا يتم الاعتماد على تاريخ جهاز المستخدم لاتخاذ قرار انتهاء الاشتراك.

## 14. الخلاصة

النظام الآن يحقق الفصل التالي:

```text
الوضع السحابي:
واجهة المستخدم -> Cloud API -> Supabase

مزامنة جهاز المستخدم:
واجهة المستخدم -> Local API -> SQLite المحلية
                              -> Cloud API -> Supabase

التحقق من الاشتراك:
واجهة المستخدم أو Local API -> Cloud API -> خدمة الاشتراك
```

تم إصلاح مشكلة الرفع التي كانت تعيد صفرًا بسبب قراءة طابور خاطئ، وأصبح رفع الجهاز يمر عبر SQLite المحلية ثم إلى السحابة. كما تم تجهيز الواجهة لعرض حالة المزامنة للمشترك بطريقة واضحة ومفهومة.

## 15. مراجعة لاحقة للاتصالين

تمت مراجعة مساري الاتصال المحلي والسحابي بعد ظهور خطأ `500` في:

```text
GET /api/v1/dashboard/activity
```

كان الاستعلام يفترض وجود أعمدة اختيارية في كل نسخ قاعدة البيانات. أصبح الآن يتحقق من الأعمدة قبل استخدامها، ويعمل مع قواعد البيانات القديمة التي لا تحتوي على `sales.sale_date` أو `sales.user_id` أو `purchases.status`.

كما تم تحسين جلسة المصادقة بحيث:

- يحفظ الخادم `refresh_token` في Cookie من نوع `HttpOnly`.
- تستخدم طلبات تسجيل الدخول والتحديث والخروج `credentials: include`.
- يسمح CORS بالطلبات الموثقة من أصول الواجهة المحددة فقط.
- يعرض التطبيق زر تسجيل خروج عند تعذر التحقق من الاشتراك.
- يعيد زر إعادة التحقق تجديد Cloud Token من Cookie قبل إعادة التحقق.

تمت إضافة اختبار توافق خاص بمخطط النشاط القديم، ونجحت اختبارات dashboard وauth وAPI وmiddleware وبناء الواجهة.
