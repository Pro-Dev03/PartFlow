# مرجع حماية تسجيل الدخول والاشتراك والاتصال السحابي

> **هذا التقرير قديم وتم استبداله.** قرارات النشر تغيرت إلى متجر واحد دون تفعيل عزل `080`; كما أضيف الترحيل `083_access_session_version.sql` بعد تنفيذ ترحيلي 081 و082. استخدم [سياسة الأمان والتحديثات الحالية](SECURITY-POLICY-AND-CHANGES-2026-09-25.md) كمرجع. لا تنفذ خطوات الترحيل أو النشر أدناه قبل مطابقتها مع التقرير الحالي.

**التاريخ:** 2026-09-25

**حالة العمل:** تعديلات الكود واختباراته المحلية مكتملة. الموقع وAPI على Render متاحان، لكن التغييرات الجديدة لم تُنشر بعد، وترحيل عزل المتاجر في Supabase لم يُنفّذ. لذلك لا تعتبر الحماية الجديدة فعالة على الخدمة الحية حتى إتمام خطوات النشر في نهاية هذا التقرير.

## هدف الحماية وحدودها

- الخادم السحابي هو مرجع الحساب والاشتراك وبيانات العمل. تغيير واجهة العميل أو قاعدة SQLite لا يمنح وصولاً إلى بيانات Render.
- تُرسل المبيعات والمخزون وسائر عمليات العمل إلى API Render في وضع الاتصال المحلي ووضع الاتصال السحابي. SQLite على الجهاز مخزن جهاز وصيانة/نسخة محلية؛ لا يُعتمد عليها لمنح الاشتراك أو صلاحيات العمل.
- عند تعديل الواجهة أو تغيير عنوان API في المتصفح، يظل الخادم السحابي يتحقق من JWT وحالة الحساب والاشتراك وعزل المتجر. العمليات المرفوضة من الخادم لا تصبح مقبولة بتجاوز شاشة الدخول.
- لا توجد طريقة برمجية تمنع مالك الجهاز من تشغيل نسخة تنفيذية معدلة أو العبث بنسخته المحلية. الحماية هنا تمنع النسخة المعدلة من اكتساب صلاحية سحابية أو تغيير قرار الاشتراك من العميل. البيانات التي لا تزال موجودة محلياً تقع تحت سيطرة مالك الجهاز.

## مسار الموقع والتطبيق المكتبي

- واجهة الموقع المنشورة: https://partflow-hpv7.onrender.com/#/login
- API الأعمال والمصادقة: https://partflow-api.onrender.com/api/v1
- عنوان API السحابي ثابت في واجهة العميل، ولا يقبل override محفوظاً في localStorage.
- طلبات الأعمال تستخدم API Render في الوضعين المحلي والسحابي. نقطة SQLite مخصصة لعمليات قاعدة الجهاز، وواجهة الويب لا تعرض أدوات SQLite الإدارية.
- التطبيق المكتبي المعبأ يستخدم الآن أصلاً آمناً هو partflow://app بدلاً من أصل file:// المبهم null. يسمح ذلك بإضافته إلى CORS كأصل محدد أثناء اتصال Electron المباشر بالسحابة. مصدر التطوير المحلي http://localhost:5174 مسموح في إعدادات التطوير.
- إعداد الإنتاج الموصى به لـ CORS_ALLOWED_ORIGINS هو قائمة مفصولة بفواصل تتضمن https://partflow-hpv7.onrender.com وpartflow://app. لا تضف النجمة * أو الأصل null. إذا كان للموقع المنشور اسم مختلف، أضف أصله الفعلي.

## الدخول والاشتراك والجلسات

- التسجيل العام مغلق في HTTP handler وفي auth.Service.Register. إنشاء حسابات المشتركين محصور بمسارات الإدارة المحمية؛ لا يستطيع طلب register إنشاء اشتراك نشط مجاني.
- يفحص الخادم الحساب النشط وحالة الاشتراك وتاريخ الانتهاء عند كل طلب محمي. الرموز لا تغني عن الفحص السحابي.
- الأكواد موحدة لتمييز انتهاء الاشتراك أو تعليقه أو حذف الحساب عن رفض الصلاحية وعن تعطل التحقق. أخطاء الخادم والسحابة المؤقتة تفشل مغلقة ولا تبقي التطبيق في جلسة مصادق عليها.
- Access JWT قصير العمر. ويرفض الخادم الرمز إذا كان ختم إصداره أقدم من updated_at للحساب، بهامش خمس ثوانٍ لدقة NumericDate وانحراف الساعة. تغيير كلمة المرور يبطل بذلك الرموز الحالية أيضاً.
- لا يصدر Refresh Token إلا بعد حفظ بصمته في جدول refresh_tokens. تُدار عملية التدوير والإبطال من التخزين الدائم، وغياب الجدول خطأ صريح يمنع الدخول أو التجديد أو الإبلاغ عن logout ناجح.
- يحدّث تغيير كلمة المرور كلمة المرور ويبطل كل Refresh Tokens داخل معاملة واحدة في مساري auth وusers. فشل حذف الرموز يعيد المعاملة ولا يترك كلمة مرور جديدة مع جلسات قابلة للتجديد.
- التعليق والحذف يسحبان Refresh Tokens. كما أن فحص حالة الاشتراك لكل طلب يوقف Access JWT الموجود حتى انتهاء مدته القصيرة.
- Offline Grant والتخويل المحلي المبني على ساعة الجهاز متوقفان. لا توجد مهلة 72 ساعة؛ عند تعذر اتصال القرار السحابي لا يسمح التطبيق بعمليات الأعمال ويُنظف حالة الجلسة والبيانات المؤقتة.
- logout من جهاز غير متصل ينظف أسرار الجهاز محلياً، لكن لا يمكن ضمان وصول طلب الإبطال إلى الخادم أثناء انقطاع الشبكة. تبقى الرموز السحابية محكومة بانتهائها وفحص حالة الاشتراك، ويجب إجراء logout متصل لإبطالها فوراً.

## CORS واتصال الموقع

- يرفض تحميل إعداد الإنتاج إذا كانت CORS_ALLOWED_ORIGINS تحتوي * أو null. كما يزيل middleware هذين الأصلين من قائمة الإنتاج دفاعياً.
- الأصل المنشور للموقع موجود في القائمة الافتراضية، ويُضاف partflow://app لدخول Electron. لا تُستخدم CORS كبديل عن JWT أو فحص الاشتراك.
- اتصال PostgreSQL/Supabase لا يعتمد على مفتاح قاعدة بيانات في المتصفح؛ بيانات الاعتماد تبقى في إعدادات Render الخلفية.

## عزل بيانات المتاجر في Supabase

- يضيف الترحيل 080 جداول المتاجر والعضويات وtenant_id لجداول الأعمال، ويفرض RLS مع سياسات قراءة وكتابة حسب المتجر. مصدر tenant هو عضوية المستخدم الموثقة، وليس tenant_id يرسله العميل.
- راجع [SQL الترحيل](../backend/migrations/080_tenant_isolation.sql) و[دليل النشر](../backend/migrations/080_tenant_isolation.rollout.md) قبل التنفيذ.
- يتطلب التنفيذ PostgreSQL 15 أو أحدث، نسخة احتياطية، ودور Runtime مخصصاً لا يملك BYPASSRLS ولا صلاحيات مالك الجداول. لا تستخدم دور postgres أو service_role لتشغيل API.
- تنقل البيانات الحالية إلى متجر المالك القديم المحدد في جلسة الترحيل. افحص البريد والبيانات قبل ذلك على نسخة staging؛ لا تشغّل SQL على الإنتاج قبل النسخ الاحتياطي ومراجعة المالك المقصود.
- بعد الترحيل يجب ضبط PARTFLOW_TENANT_RLS_ENABLED=true لكل خدمات API، وDATABASE_URL على دور Runtime المخصص. يتحقق بدء التشغيل من وجود مخطط RLS والصلاحيات المطلوبة، ويفشل إذا كانت ناقصة.
- يعيّن TenantScope نطاق المتجر من العضوية، يضعه في سياق PostgreSQL للطلب، ثم يمسح السياق. إذا فشل المسح يُغلق تجمع الاتصالات. أثناء هذه النسخة يُسلسَل الوصول إلى اتصال قاعدة واحد عند تفعيل RLS؛ هذا حد سعة معروف حتى نقل المستودعات إلى معاملات محكومة بكل طلب.
- يُمنع المشترك من مسارات المزامنة العامة. الاستيراد التاريخي محصور بالإدارة. Worker متوقف تحت RLS إلى أن تُنفذ مهامه بنطاق متجر صريح. Webhook الدفع يفشل مغلقاً عند غياب توجيه إلى المتجر.
- USE_SUPABASE_AUTH=true لا يفعّل مساراً ناقص التنفيذ؛ تهيئة Supabase Auth ترفضه حالياً.

## تحقق الكود

نجحت الحزم المركزة التالية:

```text
go test ./internal/auth ./pkg/config ./pkg/middleware ./internal/users ./internal/api ./internal/settings ./internal/sync ./internal/paymenttransactions ./pkg/offlinegrant ./cmd/offline-grant-keygen
```

ونجحت اختبارات الواجهة المركزة: 31 اختباراً في authStore وapi-client-auth وconfig/app. نجح npm run build:check، كما نجح node --check لملفي Electron main.js وpreload.js.

تغطي الاختبارات الجديدة رفض التسجيل العام حتى عند ضبط متغير تمكين قديم، عدم إنشاء مستخدم أو Refresh Token من Service.Register، إبطال الرموز بعد تغيير كلمة المرور، الفشل عند غياب جدول refresh_tokens، رفض إعداد CORS النجمي وnull في الإنتاج، استمرار CORS للموقع ولأصل Electron، ورفض الوصول المحلي عند تعطل قرار السحابة.

لم يُنفذ اختبار PostgreSQL متكامل على Supabase، ولم يُشغّل ترحيل 080، ولم يُختبر دخول متجرين على قاعدة staging. توجد إخفاقات قديمة معروفة خارج نطاق هذه التغييرات في اختبارات inventory وsales بسبب غياب item_history، وفي supplierreturns بسبب بيانات fixture ذات item_code مكرر.

## فحص الخدمة الحية وخطوات التفعيل

تم فحص Render بطلبات قراءة فقط في 2026-09-25:

- صفحة https://partflow-hpv7.onrender.com أعادت HTTP 200.
- مسار https://partflow-api.onrender.com/health أعاد HTTP 200 وحالة قاعدة البيانات healthy.
- طلب OPTIONS لتسجيل الدخول من أصل الموقع أعاد HTTP 204، وأعاد Allow-Origin يساوي أصل الموقع وAllow-Credentials=true.
- أظهر رد CORS الحي ترويسة X-PartFlow-Cloud-API-URL، بينما الشيفرة الحالية أزالت هذه الترويسة وتختبر عدم السماح بها. هذا دليل على أن خدمة Render ما زالت تشغّل إصداراً أقدم من ملفات هذا المستودع؛ نجاح health وCORS لا يثبت نشر الإصلاحات الأمنية.

قبل اعتبار الإصلاح نافذاً على المستخدمين:

1. خذ نسخة احتياطية من Supabase، وافحص الترحيل 080 ودليل تشغيله، ثم طبقه على staging واختبر متجرين منفصلين.
2. أعدّ CORS_ALLOWED_ORIGINS في Render بقيم الموقع وpartflow://app، من دون * أو null. تأكد أن إعدادات Render الأخرى تستخدم أسرار JWT وقاعدة البيانات الخلفية الصحيحة.
3. انشر API من هذا المصدر أولاً مع PARTFLOW_TENANT_RLS_ENABLED=true ودور قاعدة البيانات المخصص. تحقق من سجلات startup والفحوصات قبل فتح الخدمة للمشتركين.
4. انشر واجهة الموقع المبنية من هذا المصدر، وابنِ إصدار Electron جديداً لأن أصل partflow://app جزء من الحزمة.
5. اختبر الموقع: دخول صالح، كلمة مرور خاطئة، حساب معلق/منتهي، البيع والمخزون، ثم تغيير كلمة المرور ومحاولة استخدام Access وRefresh Token القديمين. كرر عمليات البيع والمخزون من Electron في وضع الاتصال المحلي.
6. اختبر متجرين وتأكد أن القراءة والتعديل بينهما ممنوعان، وأن outage أو انقطاع الإنترنت لا يفتح شاشة الأعمال بجلسة قديمة.

لا تُعلن الحماية مفعلة على Render قبل نجاح الترحيل والنشر والاختبارات اليدوية أعلاه. صحة /health وحدها تؤكد اتصال قاعدة البيانات فقط.
